# 학습 원칙

## 원칙

- 새 문서를 많이 만들기보다 기존 문서 하나를 쓸모 있게 만든다.
- 개념 설명은 실무 문제, 판단 기준, 짧은 기술 답변까지 이어서 쓴다.
- “정의는 아는데 언제 쓰는지 모르는 상태”를 완료로 보지 않는다.
- AI 답변은 초안으로만 쓰고 공식 문서, 코드, 실행 결과로 검증한다.

## 최종 목표

- 실무에서 문제를 예방하고 원인을 좁힐 수 있다.
- 기술 질문을 받으면 개념, 원리, 장단점, 실무 사례를 이어서 설명할 수 있다.
- 암기한 답변이 아니라 실제 판단 기준을 말할 수 있다.
- 각 문서를 나중에 기술 답변과 실무 체크리스트로 다시 쓸 수 있다.

## 학습 루프

1. [[00-home/daily-study-board|daily-study-board]] 또는 [[00-home/mastery-map|mastery-map]]에서 학습할 주제를 고른다.
2. 해당 주제 인덱스에서 질문 하나를 고른다.
3. 기존 문서가 있으면 보강하고, 없으면 `_templates/concept-template.md`로 작은 문서 하나를 만든다.
4. 실무에서 문제가 되는 상황을 먼저 쓴다.
5. 동작 원리와 해결 절차를 쓴다.
6. 한계, 부작용, 잘못 쓰는 경우를 쓴다.
7. 마지막에 면접에서 말할 짧은 답변과 꼬리 질문을 남긴다.

## 완료 기준

아래 항목 중 하나라도 없으면 아직 미완성이다.

| 항목 | 확인 질문 |
|---|---|
| 문제 상황 | 이 개념을 모르면 어떤 버그, 장애, 성능 문제가 생기는가? |
| 동작 원리 | 내부에서 어떤 순서로 동작하는가? |
| 판단 기준 | 어떤 상황에서 쓰고, 어떤 상황에서 피해야 하는가? |
| 트레이드오프 | 성능, 정합성, 복잡도, 운영 비용 중 무엇을 잃는가? |
| 검증 방법 | 로그, 테스트, 실행 계획, 메트릭 등으로 어떻게 확인하는가? |
| 기술 답변 | 1분 안에 정의, 원리, 실무 예시를 말할 수 있는가? |

## 문서 작성 순서

순서는 “정의 → 원리 → 실무”가 아니라 “문제 → 원리 → 판단”이다.

1. 어떤 문제가 생기는지 쓴다.
2. 왜 그런 문제가 생기는지 원리를 쓴다.
3. 해결 옵션을 비교한다.
4. 실무 체크리스트를 남긴다.
5. 짧은 기술 답변으로 압축한다.

## 문체 기준

사람이 소리 내어 읽어도 걸리지 않게 쓴다. AI로 초안을 만들 때도 이 기준으로 다듬는다.

**문서 구조**

- 제목 바로 아래 1~3문장으로 시작한다. 무엇이고 왜 신경 써야 하는지. `## 한 줄 정의` 같은 제목은 달지 않는다.
- 내용이 있는 섹션만 만든다. 실수·체크리스트·한계가 겹치면 `## 자주 깨지는 곳` 하나로 합친다.
- 개념 노트 끝은 `## 면접에서 말하기`(소리 내어 말할 2~4문장, 합니다체) → `## 꼬리 질문` → `## 점검 퀴즈`(있을 때) → `## 내 사례`(있을 때) → `## 관련 문서` 순서다.
- 섹션 제목은 내용을 말하게 쓴다. "확인 방법"보다 "운영에서 볼 것".

**문장**

- 한 문장에 한 생각. 섹션 첫 문장이 결론이다.
- 추상 대신 구체: "부하가 증가할 수 있다" → "만료 순간 같은 key의 miss가 한꺼번에 DB로 간다".
- 항상 그렇다면 단정한다. "~할 수 있다"는 정말 조건부일 때만 쓴다.
- 쓰지 않는 표현: "중요하다", "핵심이다", "반드시", "적절한", "효과적으로", "고려해야 한다", "~를 통해", "~측면에서", "다음과 같다", "정리하면".
- 굵게는 한 문단에 하나까지. 개수를 맞추려고 항목을 채우지 않는다.
- 본문은 한다/이다체, 면접 답변 인용문은 합니다체.

**정확성**

- 다듬을 때 기술 사실, 숫자, 버전, 조건을 바꾸지 않는다. 확신이 없으면 문장만 고친다.
- 숫자와 주장은 원문이나 공식 문서로 확인한 것만 쓴다.
