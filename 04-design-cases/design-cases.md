# 설계 사례

직접 겪은 일은 [[work-cases|내 실무 사례]]에 쓰고, 여기에는 백엔드에서 자주 만나는 설계 문제를 직접 풀어 본 글을 모은다. 동작과 한계는 공식 문서로 확인하고, 비슷한 실무 사례가 있으면 링크로 잇는다.

다른 회사가 공개한 구조를 정리할 때는 두 부분을 나눠 쓴다.

- 공개 자료로 본 구조: 기술 블로그나 발표 링크를 확인한 날짜와 같이 남긴다. 자료에 없는 내용은 추측이라고 밝힌다.
- 내 설계: 같은 문제를 내가 설계한다면 어떻게 할지 쓴다. 비슷한 실무 사례가 있으면 [[work-cases]]의 글로 잇는다.

## 사례 1: 조회 API 성능 개선

### 문제

데이터가 늘어난 뒤 목록 조회 API 응답이 느려졌다. 로컬이나 개발 환경에서는 재현되지 않았다. 운영과 비슷한 데이터 크기에서 특정 검색 조건과 정렬을 함께 쓸 때 지연이 커졌다.

### 원인 가설

처음엔 애플리케이션 로직부터 의심하기 쉽다. 조회 API라면 먼저 아래를 하나씩 따로 확인한다.

- 쿼리 수가 늘었나
- SQL 하나의 실행 시간이 긴가
- 정렬, 페이징, count query가 병목인가
- 응답 데이터가 너무 큰가

SQL 로그와 쿼리 수를 보니 N+1은 아니었다. 실행 계획을 보니 검색 조건과 정렬 조건에 맞는 인덱스를 제대로 타지 못하고 있었다.

### 확인 방법

- 애플리케이션 로그에서 API가 걸린 시간과 실행된 SQL 수를 본다.
- slow query 로그나 쿼리 프로파일러로 오래 걸리는 SQL을 찾는다.
- `EXPLAIN`으로 접근 방식, 쓰는 인덱스, 예상 행 수, 정렬 방식을 확인한다.
- 운영과 비슷한 데이터 분포에서 개선 전후 응답 시간을 비교한다.
- 목록 쿼리와 count 쿼리를 나눠서 각각 얼마나 드는지 본다.

### 해결

검색 조건과 정렬 조건에 맞춰 복합 인덱스를 다시 잡았다. 목록 조회는 projection으로 필요한 컬럼만 돌려주게 했고, offset이 커서 느린 경로는 커서 기반 조회로 바꿀지 따져 봤다.

JPA 연관 조회가 필요한 화면에도 fetch join을 무조건 넣지는 않았다. 행이 불어날 수 있는지, 페이지네이션에 걸리는 제약은 없는지 같이 확인했다. 단순 목록 화면은 DTO 조회로 바꿔서 엔티티를 줄줄이 읽어 오는 비용을 없앴다.

### 한계

- 인덱스는 조회를 빠르게 하지만 쓰기 비용과 저장 공간을 늘린다.
- 특정 검색 조건에 맞춘 인덱스는 다른 조건에서는 효과가 없기도 하다.
- 커서 기반 페이징은 offset이 클 때 느려지는 문제를 줄이지만, 원하는 페이지로 바로 건너뛰기는 어렵다.
- fetch join은 N+1을 줄이지만, 다대다 관계에서는 중복 행이 생기고 메모리를 많이 쓴다.

### 한 번에 설명하기

> 조회 API가 느려지면 애플리케이션 로직, 쿼리 수, SQL 하나의 비용을 나눠서 봅니다. SQL 로그로 N+1인지 확인하고, 느린 SQL은 `EXPLAIN`으로 인덱스를 타는지, 몇 행을 읽는지, 어떻게 정렬하는지 봅니다.
>
> 고칠 때는 인덱스만 추가하고 끝내지 않고 projection, fetch 전략, 페이징 방식, count 쿼리 비용까지 같이 봅니다.
>
> 고친 뒤에는 운영과 비슷한 데이터 크기에서 p95 응답 시간과 DB 지표를 비교해서, 효과가 있었는지와 다른 문제가 생기지 않았는지 확인합니다.

## 사례 2: Redis 캐싱 적용

### 문제

같은 조회가 반복되는 API에서 DB 부하와 응답 시간이 같이 올랐다. 데이터는 자주 읽히지만 거의 바뀌지 않았다. 그런데 모든 요청이 DB를 직접 조회해서, 사용자가 몰리는 시간대에 DB 커넥션을 많이 쓰고 있었다.

### 원인 가설

먼저 느린 원인이 쿼리 자체인지, 같은 결과를 반복해서 조회하는 구조인지, 응답을 만드는 비용인지 나눈다. 이 사례에서는 쿼리 튜닝만으로는 반복 조회 비용을 줄이기 어려웠다. 같은 조건의 조회가 짧은 시간에 여러 번 반복되고 있었다.

### 확인 방법

- access log와 쿼리 수를 보고 캐시를 붙일 만한 API를 찾는다.
- 데이터가 얼마나 자주 바뀌는지, 옛 값이 얼마나 오래 보여도 되는지 정리한다.
- 캐시 적용 전후 DB QPS, latency, Redis hit ratio를 비교한다.
- 캐시가 죽었을 때 DB와 애플리케이션이 버틸 수 있는지, fallback 기준을 확인한다.

### 해결

Cache Aside로 먼저 캐시를 보고, 없으면 DB에서 읽어 TTL과 함께 저장했다. 원본 데이터가 바뀌는 경로에서는 관련 캐시 key를 지우거나 TTL을 짧게 잡아서, 옛 값이 보이는 시간을 줄였다. 캐시 key에는 조회 조건을 빠짐없이 넣고, 결과가 null이어도 짧게 캐싱해서 같은 miss가 반복되지 않게 했다.

### 한계

- 캐시와 원본 데이터가 잠깐씩 다를 수밖에 없다.
- TTL이 길면 옛 값이 오래 남고, 짧으면 hit ratio가 떨어진다.
- Redis가 죽으면 트래픽이 DB로 몰리니 fallback과 rate limit이 필요하다.
- 캐시 key를 잘못 만들면 다른 요청의 응답을 돌려주게 된다.

### 한 번에 설명하기

> 캐시를 붙이기 전에 정말 같은 조회가 반복되는지, 데이터가 얼마나 자주 바뀌고 옛 값을 얼마나 보여 줘도 되는지부터 확인합니다.
>
> Cache Aside는 구현이 단순하지만, 원본이 바뀐 뒤 캐시가 지워지기 전까지는 둘이 다릅니다. 그래서 key 설계, TTL, 데이터가 바뀔 때 캐시를 지우는 규칙, Redis가 죽었을 때의 fallback을 같이 정합니다.
>
> 적용한 뒤에는 hit ratio만 보지 않고 DB QPS, p95 latency, Redis 오류율을 함께 봅니다.

## 사례 3: 외부 API 중복 요청 처리

### 문제

외부 API 호출이 timeout으로 실패했는데, 실제로는 외부 시스템에서 처리가 끝나 있던 경우가 있었다. 이때 클라이언트나 서버가 재시도하면 같은 요청이 두 번 처리된다.

### 원인 가설

timeout은 실패가 아니라 결과를 모르는 상태일 수 있다. 그래서 네트워크 실패, 외부 처리 성공, 응답 유실, 서버 재시도 중 어디에서 중복이 생기는지 나눠서 확인한다.

### 확인 방법

- 요청마다 business key나 idempotency key가 있는지 본다.
- timeout, retry, 외부 API 응답 상태를 trace id로 잇는다.
- 같은 key로 요청이 동시에 들어올 때 DB unique 제약이나 상태 전이가 중복 처리를 막는지 테스트한다.
- 실패한 뒤 재시도해도 결국 같은 결과가 되는지 확인한다.

### 해결

같은 요청을 다시 보낼 때는 같은 idempotency key를 쓰게 했다. 서버는 key, payload hash, 처리 상태를 저장하고, 이미 끝난 요청이면 저장해 둔 결과를 돌려줬다. 외부 API가 idempotency key를 지원하면 같은 key를 넘기고, 지원하지 않으면 우리 쪽 상태 전이와 unique 제약으로 중복 처리를 막았다.

### 한계

- 같은 key로 다른 payload가 들어오면 어떻게 할지 따로 정해야 한다.
- 외부 API가 멱등키를 지원하지 않으면 우리 쪽에서 막을 수 있는 범위가 좁아진다.
- key 보관 기간이 짧으면 늦게 온 재시도를 막지 못한다.
- timeout 뒤 결과를 확인할 API가 없으면 보상 처리나 사람이 직접 확인하는 절차가 필요하다.

### 한 번에 설명하기

> 외부 API timeout은 처리 실패가 아니라 결과를 모르는 상태로 봅니다.
>
> 재시도해도 두 번 처리되지 않게, 같은 요청에는 idempotency key를 붙이고 key와 payload hash, 처리 상태를 저장합니다. 이미 끝난 key가 다시 오면 같은 결과를 돌려주고, payload가 다르면 충돌로 처리합니다.
>
> 외부 시스템이 멱등키를 지원하지 않으면, 우리 쪽 상태 전이와 unique 제약으로 막을 수 있는 중복이라도 막습니다.

## 사례 4: 배치 안정화

### 문제

주기적으로 도는 배치가 중간에 실패하면 어디까지 처리됐는지 알기 어려웠다. 다시 돌리면 일부 데이터가 두 번 처리되고, 안 돌리면 빠진 데이터가 남았다.

### 원인 가설

배치가 불안한 건 대개 스케줄러보다 처리 단위와 재처리 기준 때문이다. 언제 실패했는지, 처리 완료를 어떻게 표시하는지, 두 번 실행될 수 있는지, 작업마다 두 번 돌려도 괜찮은지를 확인한다.

### 확인 방법

- 작업 단위마다 `pending`, `processing`, `completed`, `failed` 같은 상태가 남는지 본다.
- 배치 실행 id, 처리 건수, 실패 건수, 마지막으로 처리한 위치를 로그와 메트릭으로 남긴다.
- 같은 작업을 두 번 실행해도 결과가 깨지지 않는지 테스트한다.
- 이전 실행이 끝나기 전에 다음 실행이 시작되는지 확인한다.

### 해결

큰 작업을 chunk 단위로 나누고, chunk나 대상 행마다 처리 상태를 저장했다. 두 번 실행되면 위험한 작업은 lock이나 스케줄러의 concurrency policy로 겹치지 않게 했다. 실패한 작업은 실패 사유와 재시도해도 되는지를 남기고, 다시 처리하는 대상은 `failed` 상태이거나 정해 둔 기준 이후의 데이터로만 좁혔다.

### 한계

- 상태 테이블과 재처리 로직이 생겨서 구현이 복잡해진다.
- 외부 API 호출이 끼면 내부 상태만으로는 정확한 결과를 알 수 없다.
- lock을 걸어도 멱등성이 생기지는 않는다.
- 처리 단위를 너무 작게 나누면 관리 비용이, 너무 크게 나누면 재처리 비용이 커진다.

### 한 번에 설명하기

> 배치는 실패하지 않게 만드는 것보다, 실패했을 때 어디서부터 다시 시작할지 알 수 있게 만드는 게 먼저입니다. 처리 단위를 chunk로 나누고 단위마다 상태, 실행 id, 처리 건수, 실패 사유를 남깁니다.
>
> 다시 돌려도 결과가 깨지지 않게 만들고, 두 번 실행되면 위험한 작업은 lock이나 CronJob concurrency policy로 막습니다.
>
> 운영할 때는 성공했는지만 보지 않고 처리 건수, 실패 건수, 실행 시간에도 알림을 겁니다.

## 사례 5: 배포 안정화

### 문제

새 버전을 배포한 뒤 일부 API의 오류율이 올랐는데, 배포 자체는 성공으로 표시됐다. 코드 문제인지, 설정 문제인지, 새 Pod가 덜 준비된 건지 가려내는 데 시간이 걸렸다.

### 원인 가설

배포가 제대로 됐는지는 pipeline이 성공했다는 것만으로 알 수 없다. 새 버전 Pod의 readiness, 설정이 제대로 들어갔는지, error rate, latency, 롤백할 수 있는지를 함께 확인한다.

### 확인 방법

- rollout status와 Pod event를 본다.
- 배포 전후 error rate, p95 latency, restart count, readiness failure를 비교한다.
- ConfigMap, Secret, image tag가 의도한 값인지 확인한다.
- 롤백할 때 DB 스키마와 설정이 이전 버전과 맞는지 확인한다.

### 해결

readiness probe로 준비된 Pod만 트래픽을 받게 하고, rolling update 중에도 쓸 수 있는 Pod 수가 줄지 않게 설정했다. 배포 뒤 일정 시간 동안 주요 지표를 지켜보고, 오류율이 기준을 넘으면 롤백하는 절차를 만들었다. 설정 변경과 코드 변경은 되도록 따로 배포해서 문제가 생겼을 때 원인을 쉽게 찾게 했다.

### 한계

- rollback은 Pod template은 되돌리지만 DB migration이나 외부 상태 변경은 자동으로 되돌리지 못한다.
- readiness 기준이 틀리면 배포 전략이 있어도 장애를 막지 못한다.
- 지표 기준이 없으면 배포가 성공했는지 자동으로 판단하기 어렵다.
- replica가 너무 적으면 rolling update 중 가용성을 지키기 어렵다.

### 한 번에 설명하기

> pipeline이 끝났다고 배포가 성공한 건 아닙니다. 새 버전이 띄워진 뒤에도 지표가 정상인지까지 확인해야 합니다. Kubernetes에서는 rollout 상태, readiness, Pod event, error rate, latency를 같이 봅니다.
>
> 서비스를 거의 멈추지 않고 배포하려면 replica 수, readiness probe, rolling update 전략이 서로 맞아야 합니다.
>
> 롤백할 준비는 해 두되, DB나 외부 상태를 바꾸는 배포라면 이전 버전과 함께 돌아도 문제가 없게 먼저 설계합니다.

## 사례 6: 로그/알림 개선

### 문제

장애가 나면 사용자 요청이 어떻게 흘러갔는지 따라가기 어려웠다. 로그는 많았지만, 어떤 요청에서 어떤 외부 호출과 DB 작업이 이어졌는지 묶어 볼 수 없었다. 알림은 늦거나 너무 많이 왔다.

### 원인 가설

장애를 추적하기 어려운 건 로그가 모자라서가 아니라, 알고 싶은 것에 답해 줄 신호가 없어서일 때가 많다. 장애를 분석하는 데 필요한 trace id, 중요한 상태 변화 로그, 지표, 알림 기준이 있는지 확인한다.

### 확인 방법

- 요청 시작부터 외부 API, DB, 비동기 처리까지 같은 trace id가 전달되는지 본다.
- 오류 로그에 사용자를 알아볼 수 있는 민감 정보 없이, 원인이 어떤 종류인지는 남는지 본다.
- latency, error rate, saturation 지표가 endpoint나 dependency 단위로 있는지 확인한다.
- 알림이 SLO나 사용자가 실제로 겪는 문제와 이어지는지 확인한다.

### 해결

요청마다 붙이는 trace id와 correlation id 형식을 통일하고, 외부 API 호출과 비동기 메시지에도 넘겼다. 로그는 모든 값을 남기지 않고 상태 전이, 실패 사유, 호출한 외부 의존성, 걸린 시간 위주로 정리했다. 알림은 단순 오류 개수 대신 오류율, p95 latency, 주요 배치 실패처럼 받으면 바로 움직일 수 있는 조건으로 바꿨다.

### 한계

- 로그를 늘리면 비용이 들고, 쓸모없는 로그도 같이 는다.
- trace id가 한 군데에서라도 넘어가지 않으면 흐름이 끊긴다.
- 알림 기준이 낮으면 알림이 너무 많아 무뎌지고, 높으면 장애를 늦게 안다.
- 민감 정보 마스킹 없이 로그를 늘리면 보안 위험이 커진다.

### 한 번에 설명하기

> 장애를 빨리 분석하려면 로그가 많은 것보다, 로그끼리 이어서 볼 수 있는 게 중요합니다. 요청마다 trace id를 붙이고 외부 API와 비동기 처리까지 넘겨서 흐름을 잇습니다.
>
> 로그는 상태 변화, 실패 사유, 호출한 외부 의존성, 걸린 시간 위주로 남기고 민감 정보는 뺍니다.
>
> 알림은 로그 개수가 아니라, 사용자가 실제로 겪는 문제와 이어지는 오류율, 지연 시간, 실패율로 겁니다.
