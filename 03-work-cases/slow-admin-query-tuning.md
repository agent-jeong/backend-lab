# 5초 걸리던 관리자 조회를 실행계획으로 고치기

임직원 휴양시설 예약 시스템의 관리자 예약 내역 화면이 열릴 때마다 5초쯤 걸렸다. 운영 담당자가 매일 쓰는 화면이었다.

짐작으로 고치지 않고 실행계획부터 봤다. 풀 스캔(`type: ALL`)이 나오고 있었고, 원인은 두 가지였다. 목록 행마다 서브쿼리가 돌았고, 컬럼에 함수가 씌워져 있었다. 이 둘을 고치고 복합 인덱스를 만든 뒤, 부하 테스트에서 예약 내역 조회 p95 90ms를 확인했다.

| 구분 | 내용 |
|---|---|
| 증상 | 관리자 예약 내역 화면이 열리는 데 약 5초 |
| 원인 | 목록 행마다 도는 스칼라 서브쿼리, 날짜 컬럼에 씌운 포맷 함수, 검색 조건에 맞는 인덱스 없음 |
| 해결 | 서브쿼리를 조인과 합계로 바꾸고, 함수는 비교값 쪽으로 옮기고, 등호, 범위, GROUP BY 컬럼 순서로 복합 인덱스를 만들었다 |
| 결과 | 부하 테스트(10초 동안 600요청)에서 예약 내역 조회 p95 90ms, 실패 0건 |
| 남은 것 | 같은 날 손본 급여 공제 조회는 부하 시 평균 1.45초 |

## 1. 실행계획에서 본 것

기존에도 인덱스는 있었다(PK, 그룹 코드, 객실 ID). 하지만 화면의 검색 조건인 "확정 여부"와 "숙박 시작일"에 맞는 인덱스가 없었다. 시작일에는 함수까지 씌워져 있어서, 인덱스를 만들어도 탈 수 없는 쿼리였다.

## 2. 고친 것 네 가지

### 행마다 도는 서브쿼리를 조인으로

목록의 예약마다 투숙 금액을 같이 보여 줘야 했다. 원래는 행마다 "이 객실의 숙박 날짜 가격을 더하라"는 서브쿼리가 따로 돌았다. 목록이 천 건이면 그 계산도 천 번 돈다.

```sql
-- 전: 목록 행마다 실행
SELECT r.*,
       (SELECT SUM(a.price)
          FROM room_available a
         WHERE a.room_id = r.room_id
           AND a.date_available BETWEEN r.start_date AND r.end_date) AS total_price
  FROM reservation r
 WHERE ...;

-- 후: 한 번 조인하고 예약별로 묶어 합계
SELECT r.id, ..., SUM(a.price) AS total_price
  FROM reservation r
  LEFT JOIN room_available a
         ON a.room_id = r.room_id
        AND a.date_available BETWEEN r.start_date AND r.end_date
 WHERE ...
 GROUP BY r.id, ...;
```

조인하면 행이 박 수만큼 늘어난다. 2박 예약이면 날짜별 가격 두 줄이 붙고, 예약 id로 묶어 한 줄로 만든다. 처음엔 INNER JOIN이었는데, 가격 데이터가 없는 예약이 목록에서 빠져서 LEFT JOIN으로 바꾸고 없으면 0원으로 보이게 했다.

서브쿼리라서 무조건 느린 건 아니다. 인덱스를 타면 괜찮다. 여기서는 서브쿼리 안에서도 인덱스를 못 타서 매번 많이 읽은 게 문제였다.

### 컬럼에 씌운 함수를 비교값 쪽으로

```sql
-- 전: 컬럼을 가공해서 비교 → 인덱스를 못 탄다
WHERE DATE_FORMAT(start_date, '%Y.%m.%d') >= ?

-- 후: 입력값을 컬럼 형식에 맞춘다
WHERE start_date >= REPLACE(?, '.', '')
```

인덱스는 컬럼의 원래 값으로 정렬돼 있다. 함수를 씌운 결과로 비교하면 인덱스에서 범위를 찾을 수 없다.

### 조건 순서에 맞춘 복합 인덱스

| 테이블 | 인덱스 | 이 순서로 둔 이유 |
|---|---|---|
| 예약 | (확정 여부, 시작일, 신청자, 신청 시각) | 등호 조건, 범위 조건, GROUP BY 컬럼 순서 |
| 객실 가용일 | (객실 ID, 가용 날짜) | 객실별 날짜 범위 조회. 앞부분이 겹치는 단일 인덱스는 지웠다 |

등호인 확정 여부를 맨 앞에, 범위인 시작일을 그다음에 뒀다. 범위 조건 뒤의 컬럼은 인덱스를 따라 찾아 내려가는 데 쓰이지 못하므로, 거르는 조건이 아닌 GROUP BY 컬럼을 맨 뒤에 붙였다. 그래도 인덱스에 들어 있으니 GROUP BY와 SELECT가 테이블을 덜 읽는다.

### 힌트는 마지막 수단으로

`USE INDEX` 힌트를 줬는데도 옵티마이저가 풀 스캔을 골랐다. 인덱스를 거쳐 읽는 비용을 더 크게 본 것 같았다. 그래서 `FORCE INDEX`로 `range` 접근이 되는 걸 확인하고 썼고, 쿼리 주석에 실행계획 결과를 남겼다.

`FORCE INDEX`에는 대가가 있다. 데이터 분포가 바뀌어도 옵티마이저가 다른 방법을 고르지 못한다. 그래서 쿼리 모양을 먼저 고치고, 그래도 안 될 때만 쓴다.

같은 날 급여 공제 조회도 손봤다. 전체 결과에 `ROW_NUMBER()`로 번호를 매긴 뒤 자르던 페이징을 `GROUP BY + LIMIT/OFFSET`으로 바꿔 필요한 만큼만 읽게 했다.

## 3. 효과를 어떻게 확인했나

튜닝 4주 뒤 Gatling으로 부하를 줬다.

| 항목 | 내용 |
|---|---|
| 대상 | 예약 시스템 조회 API 8개 |
| 부하 | 10초 동안 가상 사용자 600명이 나눠 들어옴(초당 약 60요청) |
| 합격 기준(코드로 검증) | 실패 0건, 최대 응답 5초 미만, p95 3초 미만, 성공률 99% 초과 |
| 결과 | 모두 통과. 7개 API 평균 0.07~0.27초, 예약 내역 조회 p95 90ms |
| 눈에 띈 것 | 급여 공제 조회만 평균 1.45초. 전체 p95가 1.4초로 나온 것도 이 API 때문이다 |

- 평균이 아니라 p95를 기준으로 걸었다. 평균만 보면 느린 몇 건이 묻힌다. 전체 p95가 튄 덕분에 급여 공제 조회가 따로 느리다는 걸 바로 찾았다.
- 동시 접속 수를 고정하지 않고, 요청이 일정한 속도로 들어올 때 버티는지를 봤다.
- 시나리오와 합격 기준을 코드로 저장소에 남겨서 다시 돌릴 수 있게 했다.

### 숫자를 말할 때 조심할 것

튜닝 전 5초는 브라우저 네트워크 탭의 경과 시간으로 본 값이다. 튜닝 후 90ms는 부하 테스트의 p95다. 재는 방법이 달라서 "몇 배 빨라졌다"고 말하지 않는다. "5초 걸리던 화면이 부하를 줘도 p95 90ms 안에 들어온다"고 말하는 게 맞다. 또 이 수치는 예약 내역 조회 기준이다.

## 다시 한다면

1. 튜닝하기 전에도 같은 부하 테스트를 돌려 둔다. 그래야 전후를 같은 기준으로 비교할 수 있다.
2. 급여 공제 조회는 실행계획을 다시 떠서 어디서 읽는 행이 많은지부터 본다. 기간 조건에 맞는 인덱스를 만들거나, 집계를 미리 쌓아 두는 방식을 따져 본다.
3. `FORCE INDEX`가 남은 쿼리는 점검 목록에 올려 두고, 데이터가 늘면 실행계획을 다시 확인한다.

## 한 번에 설명하기

### 60초 요약

> 휴양시설 예약 시스템에서 관리자 예약 내역 화면이 열릴 때마다 5초쯤 걸렸습니다. 짐작으로 고치지 않고 실행계획부터 봤더니 풀 스캔이 나오고 있었습니다.
>
> 원인은 두 가지였습니다. 목록 행마다 투숙 금액을 계산하는 서브쿼리가 반복해서 돌았고, 시작일 컬럼에 날짜 포맷 함수를 씌워 비교해서 인덱스를 탈 수 없었습니다.
>
> 서브쿼리는 조인 한 번과 합계로 바꾸고, 함수는 비교값 쪽으로 옮기고, 등호, 범위, GROUP BY 순서로 복합 인덱스를 만들었습니다. 이후 부하 테스트에서 예약 내역 조회가 p95 90ms, 실패 0건으로 나왔습니다.

### 꼬리 질문

| 질문 | 한 줄 답 |
|---|---|
| 몇 배 빨라졌나? | 전후를 잰 방법이 달라서 배수로는 말하지 않습니다. 5초 걸리던 화면이 부하를 줘도 p95 90ms 안에 들어온다고 말합니다 |
| 왜 그 컬럼 순서? | 등호 조건을 앞에, 범위 조건을 그다음에 뒀습니다. 범위 조건 뒤에 오는 컬럼은 인덱스를 따라 찾아 내려가는 데 쓰이지 못하거든요 |
| `USE INDEX`와 `FORCE INDEX` 차이? | USE는 힌트라서 옵티마이저가 무시할 수 있습니다. FORCE는 풀 스캔 비용을 아주 크게 보게 만들어서 사실상 그 인덱스를 쓰게 합니다 |
| OFFSET 페이징은 뒤로 갈수록 느린데? | 맞습니다. 깊은 페이지까지 보면 커서 페이징이 맞습니다. 이 운영 목록은 필터로 좁혀서 앞 페이지만 보기 때문에 OFFSET으로 충분했습니다 |
| 왜 평균이 아니라 p95? | 평균만 보면 느린 몇 건이 묻힙니다. 20명 중 1명이 겪는 느림까지 보려고 p95로 기준을 잡았습니다 |
| 남은 문제는? | 급여 공제 조회가 부하를 주면 평균 1.45초입니다. 이것도 실행계획부터 다시 보려고 합니다 |
