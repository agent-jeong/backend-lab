# 내 실무 사례

직접 맡았던 일을 회사·시스템 이름 없이 일반화했다. 면접에서 자주 나오는 일반 설계 문제는 [[design-cases]]에 따로 모은다.

## 작성 원칙

- 회사 내부 정보는 지운다.
- 시스템명, 테이블명, URL, 로그 원문은 쓰지 않는다.
- 문제 유형과 해결 패턴 위주로 일반화한다.
- 이력서에는 결과를, 플레이북에는 원리를 쓴다.

## 사례 작성 형식

길게 쓰지 말고 문제를 풀어 간 흐름이 보이게 쓴다.

| 구간 | 쓸 내용 |
|---|---|
| 문제 | 사용자가 겪은 증상 또는 운영 지표 변화 |
| 원인 가설 | 처음 의심한 지점과 확인한 근거 |
| 확인 방법 | 로그, 메트릭, 실행 계획, 테스트, 재현 조건 |
| 해결 | 적용한 변경과 선택 이유 |
| 한계 | 남은 위험, 비용, 대안 |
| 면접에서 말하기 | 1분 안에 소리 내어 말할 답변 |

## 좋은 사례 기준

- 숫자는 공개해도 되는 범위에서만 쓴다.
- 특정 회사, 서비스, 테이블, 고객을 알아볼 수 없어야 한다.
- “개선했다”보다 “병목이나 원인을 어떻게 좁혔는가”가 보여야 한다.
- 결과만 쓰지 말고, 고르지 않은 대안과 그 이유도 쓴다.
