# 첨부파일 18만 건을 26분에 누락 없이 옮기기

전자결재 첨부파일 저장소를 한 오브젝트 스토리지에서 다른 오브젝트 스토리지로 옮겼다. 파일은 약 18만 4천 건, 55GB였다. 처음 소량을 옮겨 본 추정은 100시간이었다.

실제 운영 이관은 26분에 끝났고 오류와 누락은 0건이었다. 빨라진 이유는 병렬도를 높여서지만, 더 중요한 건 그 전에 **추정이 틀렸다는 것**을 찾은 일이다. 그리고 원본을 지우면 되돌릴 수 없는 작업이라, 속도보다 실수를 막는 장치를 먼저 만들었다.

| 구분 | 내용 |
|---|---|
| 작업 | 첨부파일 약 18만 4천 건(55GB)을 새 오브젝트 스토리지로 복사 |
| 처음 추정 | 건당 약 2초 → 100시간 |
| 실제 병목 | 작은 파일(평균 314KB)의 요청 왕복 지연, 건당 약 0.12초 |
| 해결 | 같은 200건으로 병렬도 4·16·32 비교 → 16 선택. 처리량 3.9 → 18.6 MiB/s(4.8배) |
| 검증 | 개수 비교 대신 "원본에만 있는 파일 0건"을 기준으로. 리허설과 운영 모두 누락 0건 |
| 안전장치 | 복사만 허용, 역방향 실행 차단, 중복 실행 차단, 전량 실행 전 확인 |
| 남은 것 | 최종 전환. 쓰기를 잠시 멈추고 증분 복사와 누락 검사를 다시 돌린다 |

## 1. 전체 흐름

```mermaid
flowchart LR
    A[소량 측정<br/>100시간 추정] --> B[dry-run으로<br/>고정 비용 분리]
    B --> C[같은 200건으로<br/>병렬도 비교]
    C --> D[리허설<br/>27만 건]
    D --> E[운영 1차 이관<br/>26분]
    E --> F[누락 · 잔차 검사]
    F -->|이관 중 새 파일| G[증분 복사]
```

## 2. 100시간 추정이 틀린 이유

처음 몇십 건을 옮겨 보니 건당 약 2초가 나왔다. 18만 건이면 100시간이다. 그대로 믿었다면 이관 창을 며칠로 잡았을 것이다.

이상한 점이 하나 있었다. 실제로는 복사하지 않는 dry-run도 거의 같은 시간이 걸렸다. 복사를 안 하는데 시간이 같다면, 그 시간은 복사가 아니라 다른 데서 나온다.

쪼개 보니 약 20초가 버킷 전체 목록을 읽는 시간이었다. 파일 수와 상관없이 한 번 드는 고정 비용이다. 표본이 작으니 이 20초가 건당 시간에 크게 섞여 들어가 있었다.

| 측정 | 보이는 것 | 실제 |
|---|---|---|
| 소량 복사 | 건당 약 2초 | 목록 조회 20초가 몇십 건에 나눠져 섞임 |
| 고정 비용을 뺀 뒤 | 건당 약 0.12초 | 파일 하나를 요청하고 응답받는 왕복 시간 |

**교훈: 작은 표본으로 잰 건당 시간에는 고정 비용이 섞인다.** 고정 비용과 건당 비용을 따로 재야 추정이 맞는다.

## 3. 병목은 대역폭이 아니라 왕복 지연

파일이 평균 314KB로 작았다. 작은 파일은 데이터를 보내는 시간보다 요청 한 번을 주고받는 대기 시간이 대부분이다. 한 번에 하나씩 옮기면 그 대기 동안 네트워크는 거의 놀고 있다.

그래서 요청을 여러 개 동시에 띄웠다. 대기 시간이 서로 겹치면서 같은 시간에 더 많은 파일이 옮겨진다.

병렬도는 감으로 정하지 않았다. **같은 200건**으로 4, 16, 32를 차례로 돌려 처리량과 오류를 비교했다. 파일이 다르면 크기 분포가 달라져 비교가 안 된다.

| 병렬도 | 결과 |
|---|---|
| 4 | 3.9 MiB/s |
| 16 | 18.6 MiB/s (4.8배). 오류 없음 |
| 32 | 오류는 없었지만 16과 차이가 크지 않았다 |

16을 골랐다. 시간을 더 줄이기보다 끊겨도 이어 가는 구조에 힘을 쓰는 편이 낫다고 봤고, 32는 일정이 급할 때 쓸 카드로 남겼다.

병렬도는 높을수록 좋은 값이 아니다. 상대 저장소의 요청 제한에 걸리거나 오류가 늘기 시작하면, 재시도가 쌓여 오히려 느려진다. 그래서 비교할 때 처리량과 오류를 같이 봤다.

## 4. 누락 0건을 무엇으로 확인했나

### 개수 비교를 못 쓴 이유

처음 생각한 기준은 "원본 개수 = 목적지 개수"였다. 그런데 이관하는 동안에도 앱이 파일을 실제로 지운다. 원본과 목적지 개수는 원래부터 어긋나고, 정상인 이관도 실패로 나왔다.

### 다시 세운 기준

| 기준 | 질문 | 판정 |
|---|---|---|
| 누락 검사 (필수) | 원본에는 있는데 목적지에 없는 파일이 있나? | 0건이어야 통과 |
| 잔차 검사 (보조) | 목적지에만 있는 파일은 왜 있나? | 복사 기록으로 전부 설명돼야 통과 |

누락 검사는 "옮겨야 할 것을 다 옮겼나", 잔차 검사는 "설명 못 하는 파일이 생기지 않았나"를 본다. 둘 다 키 목록을 비교하므로 앱이 중간에 지운 파일 때문에 틀리지 않는다.

### 걷어낸 기준

DB의 첨부파일 목록과 대조하는 기준도 만들었다가 뺐다. DB에서는 지워졌지만 옮겨야 하는 파일이 있어서, 이 기준은 정상 파일을 문제로 잡았다. 기준이 틀리면 검사를 통과해도 안심할 수 없다.

### 리허설

운영 전에 운영보다 많은 27만 건, 82GB로 리허설을 했다. 같은 스크립트, 같은 병렬도, 같은 검사를 돌렸다. 리허설과 1차 운영 이관 모두 오류·누락·잔차 0건이었다.

### 이관 중에 올라온 파일

운영 이관 뒤 검사에서 5건이 잡혔다. 이관이 도는 동안 새로 올라온 파일이었다. 증분 복사로 18초 만에 채웠다.

이 5건 덕분에 최종 전환 순서가 정해졌다. 쓰기를 열어 둔 채 전환하면 그 사이 올라온 파일이 빠진다. 그래서 전환 때는 **쓰기를 잠시 멈추고 → 증분 복사 → 누락 검사 → 전환** 순서로 간다.

## 5. 되돌릴 수 없는 작업의 안전장치

명령 하나만 잘못 써도 원본이 지워질 수 있었다. 사람이 조심하는 데 기대지 않고, 실수가 실행되지 않게 스크립트에 막아 뒀다.

| 막은 실수 | 장치 |
|---|---|
| 목적지를 원본과 똑같이 맞추려다 파일이 지워짐 | 복사 방식을 `copy`로 고정. 지우는 동작(`sync`)은 스크립트에서 못 쓴다 |
| 원본과 목적지를 바꿔 씀 | 방향을 검사해서 역방향 실행을 막는다 |
| 같은 작업을 두 번 띄움 | `flock`으로 작업당 하나만 돌게 한다 |
| 테스트용 명령이 전량으로 돌아감 | 전량 실행 전에 한 번 더 확인을 받는다 |

원본 저장소에는 읽기만 했다.

### `copy`와 `sync`의 차이

`sync`는 목적지를 원본과 똑같이 만들려고 **목적지에만 있는 파일을 지운다.** 방향을 반대로 쓰면 비어 있는 쪽에 맞춰 원본이 지워진다. `copy`는 없는 것만 더하고 아무것도 지우지 않는다. 이관에는 지우는 동작이 필요 없으니 아예 못 쓰게 했다.

### 접속이 끊겨도 이어 가기

관리 서버 접속이 2~3분마다 끊겼다. 접속 세션에 작업을 붙여 두면 끊길 때 작업도 같이 죽는다. `tmux`로 작업을 접속과 떼어 놓고, 끊기면 다시 붙어서 진행 상황을 봤다. 복사는 이미 옮긴 파일을 건너뛰므로 중간에 멈춰도 다시 돌리면 남은 것만 옮긴다.

## 6. 정상 vs 장애

| 상황 | 일어나는 일 | 대응 |
|---|---|---|
| 정상 | 병렬도 16으로 복사 → 누락·잔차 검사 0건 | 1차 이관 완료 |
| 관리 접속 끊김 | 작업은 `tmux` 안에서 계속 돈다 | 다시 붙어서 확인 |
| 작업 중단 | 복사가 멈춘다 | 같은 명령을 다시 돌리면 남은 파일만 옮긴다 |
| 같은 작업 두 번 실행 | `flock`이 두 번째를 막는다 | 기다리거나 앞의 작업을 확인 |
| 이관 중 새 파일 | 누락 검사에 잡힌다 | 증분 복사 |
| 방향을 바꿔 씀 | 스크립트가 시작 전에 막는다 | 명령 수정 |

## 다시 한다면

1. 처음 측정할 때부터 고정 비용(목록 조회)과 건당 비용을 나눠 잰다. 그러면 dry-run으로 되짚을 필요 없이 첫 추정부터 맞는다.
2. 누락 검사 기준을 이관 설계 단계에서 먼저 정한다. "무엇이 0이면 성공인가"를 정해야 리허설 결과를 판정할 수 있다.
3. 최종 전환 절차(쓰기 중단 → 증분 복사 → 누락 검사 → 전환)도 리허설에서 같이 돌린다.

### 60초 답변

> 첨부파일 약 18만 건, 55GB를 다른 오브젝트 스토리지로 옮기는 일을 맡았습니다. 처음 소량을 재 보니 건당 2초, 전체 100시간이 나왔습니다. 그런데 복사하지 않는 dry-run도 같은 시간이 걸려서 따져 보니, 20초가 버킷 목록을 읽는 고정 비용이었습니다. 실제 병목은 작은 파일의 요청 왕복 지연, 건당 0.12초였습니다. 같은 200건으로 병렬도 4, 16, 32를 비교해 16을 골랐고, 처리량이 4.8배가 됐습니다. 검증은 앱이 파일을 지우기 때문에 개수 비교를 못 쓰고, 원본에만 있는 파일이 0건인지 보는 누락 검사를 기준으로 삼았습니다. 원본이 지워지면 되돌릴 수 없어서 복사만 허용, 역방향 차단, 중복 실행 차단, 전량 확인을 스크립트에 넣었고, 운영 이관은 26분에 누락 0건으로 끝났습니다.

### 꼬리질문

| 질문 | 한 줄 답 |
|---|---|
| 작은 파일에서 왜 병렬이 효과가 큰가? | 전송보다 왕복 대기가 대부분이다. 요청을 동시에 띄우면 대기가 겹친다 |
| 왜 32가 아니라 16? | 32도 오류는 없었지만 차이가 크지 않았다. 끊겨도 이어 가는 구조에 집중하고 32는 남겨 뒀다 |
| 왜 같은 200건으로 비교했나? | 파일이 바뀌면 크기 분포가 달라져 병렬도 효과만 따로 볼 수 없다 |
| 누락 0건은 어떻게 아나? | 원본에만 있는 키가 0건인지 본다. 목적지에만 있는 키는 복사 기록으로 설명한다 |
| 개수 비교는 왜 안 되나? | 이관 중에도 앱이 파일을 지워서 정상도 개수가 어긋난다 |
| 왜 `sync`가 아니라 `copy`? | `sync`는 목적지에만 있는 파일을 지운다. 방향을 잘못 쓰면 원본이 사라진다 |
| 이관 중에 올라온 파일은? | 검사에서 5건이 잡혀 증분 복사로 채웠다. 그래서 최종 전환 때는 쓰기를 잠시 멈춘다 |
| 중간에 끊기면? | `tmux`로 작업을 접속과 분리했고, 다시 돌리면 이미 옮긴 파일은 건너뛴다 |

## 일반화한 교훈

- 작은 표본의 건당 시간에는 고정 비용이 섞인다. 둘을 나눠 재야 추정이 맞는다.
- 작은 파일이 많으면 병목은 대역폭이 아니라 왕복 지연이다. 병렬도는 같은 표본으로 비교해 정한다.
- 검증 기준이 틀리면 0건이 나와도 믿을 수 없다. "무엇이 0이면 성공인가"를 먼저 정한다.
- 되돌릴 수 없는 작업은 사람의 주의가 아니라 스크립트가 실수를 막게 한다.
