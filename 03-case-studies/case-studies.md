# Case Studies

- 회사 내부 정보는 지운다.
- 시스템명, 테이블명, URL, 로그 원문은 쓰지 않는다.
- 문제 유형과 해결 패턴 위주로 일반화한다.

## 사례 1: 조회 API 성능 개선

### 문제

데이터가 늘어난 뒤 목록 조회 API 응답이 느려졌다. 로컬이나 개발 환경에서는 재현되지 않았다. 운영과 비슷한 데이터 크기에서 특정 검색 조건과 정렬을 함께 쓸 때 지연이 커졌다.

### 원인 가설

처음엔 애플리케이션 로직을 의심하기 쉽다. 조회 API라면 먼저 아래를 하나씩 떼어 본다.

- 쿼리 수가 늘었나
- SQL 하나의 실행 시간이 긴가
- 정렬, 페이징, count query가 병목인가
- 응답 데이터가 너무 큰가

SQL 로그와 query count를 보니 N+1은 아니었다. 실행 계획에서 검색 조건과 정렬 조건에 맞는 인덱스를 제대로 타지 못하는 것이 원인으로 드러났다.

### 확인 방법

- 애플리케이션 로그에서 API elapsed time과 실행된 SQL 수를 본다.
- slow query 로그나 query profiler로 오래 걸리는 SQL을 찾는다.
- `EXPLAIN`으로 접근 방식, 사용 인덱스, 예상 row 수, 정렬 방식을 확인한다.
- 운영과 비슷한 데이터 분포에서 개선 전후 응답 시간을 비교한다.
- 목록 query와 count query를 나눠 각각의 비용을 본다.

### 해결

검색 조건과 정렬 조건에 맞춰 복합 인덱스를 다시 잡았다. 목록 조회는 projection으로 필요한 컬럼만 돌려주게 했고, 큰 offset이 문제가 되는 경로는 커서 기반 조회를 검토했다.

JPA 연관 조회가 필요한 화면에도 fetch join을 무조건 넣지 않았다. row가 불어날 가능성과 페이지네이션 제약을 같이 확인했다. 단순 목록 화면은 DTO 조회로 바꿔 엔티티 그래프 로딩 비용을 없앴다.

### 한계

- 인덱스는 조회를 빠르게 하지만 쓰기 비용과 저장 공간을 늘린다.
- 특정 검색 조건에 맞춘 인덱스는 다른 조건에서는 효과가 없을 수 있다.
- 커서 기반 페이징은 큰 offset 문제를 줄이지만 임의 페이지 이동에 불리하다.
- fetch join은 N+1을 줄이지만, 다대다 형태에서는 중복 row와 메모리 사용량이 커진다.

### 면접에서 말하기

> 조회 API가 느려지면 먼저 애플리케이션 로직, 쿼리 수, SQL 하나의 비용을 나눠서 봅니다. SQL 로그로 N+1인지 확인하고, 느린 SQL은 `EXPLAIN`으로 인덱스 사용 여부, scan row, 정렬 방식을 봅니다. 개선은 인덱스 추가로 끝내지 않고 projection, fetch 전략, 페이징 방식, count query 비용까지 같이 봅니다. 개선 뒤에는 운영과 비슷한 데이터 크기에서 p95 응답 시간과 DB 지표를 비교해 효과와 부작용을 확인합니다.

## 사례 2: Redis 캐싱 적용

### 문제

반복 조회가 많은 API에서 DB 부하와 응답 시간이 같이 올랐다. 데이터는 자주 읽히지만 거의 바뀌지 않았다. 그런데 모든 요청이 DB를 직접 조회해서 peak 시간대 connection 사용량이 높았다.

### 원인 가설

먼저 느린 원인이 DB query 자체인지, 같은 결과를 반복해서 조회하는 구조인지, 응답 생성 비용인지 나눈다. 이 사례에서는 query 튜닝만으로는 반복 조회 비용을 줄이기 어려웠다. 같은 조건의 조회가 짧은 시간에 많이 반복되는 패턴이 확인됐다.

### 확인 방법

- access log와 query count로 API별 캐시 후보를 찾는다.
- 데이터 변경 빈도와, 옛 값이 보여도 되는 시간을 정리한다.
- 캐시 적용 전후 DB QPS, latency, Redis hit ratio를 비교한다.
- 캐시 장애 때 DB와 애플리케이션이 버틸 수 있는지 fallback 기준을 확인한다.

### 해결

Cache Aside로 먼저 캐시를 보고, 없으면 DB에서 읽어 TTL과 함께 저장했다. 원본 데이터가 바뀌는 경로에서는 관련 cache key를 지우거나 TTL을 짧게 잡아 옛 값이 보이는 시간을 제한했다. 캐시 key에는 조회 조건을 빠짐없이 넣고, null 결과도 짧게 캐싱해 같은 miss가 반복되지 않게 했다.

### 한계

- 캐시와 원본 데이터 사이에 잠깐씩 차이가 생긴다.
- TTL이 길면 옛 값이 오래 남고, 짧으면 hit ratio가 떨어진다.
- Redis 장애 때 트래픽이 DB로 몰릴 수 있어 fallback과 rate limit이 필요하다.
- 캐시 key 설계가 틀리면 다른 요청의 응답을 재사용한다.

### 면접에서 말하기

> 캐시를 붙이기 전에 먼저 반복 조회가 맞는지, 데이터가 얼마나 자주 바뀌고 옛 값을 얼마나 보여 줘도 되는지 확인합니다. Cache Aside는 구현이 단순하지만 원본 변경과 캐시 무효화 사이에 차이가 생깁니다. 그래서 key 설계, TTL, 변경 시 삭제 정책, Redis 장애 때의 fallback을 같이 정합니다. 적용한 뒤에는 hit ratio만이 아니라 DB QPS, p95 latency, Redis 오류율을 함께 봅니다.

## 사례 3: 외부 API 중복 요청 처리

### 문제

외부 API 호출이 timeout으로 실패했는데, 실제로는 외부 시스템에서 처리가 끝난 경우가 있었다. 이때 클라이언트나 서버가 재시도하면 같은 업무 요청이 두 번 처리될 수 있었다.

### 원인 가설

timeout은 실패가 아니라 결과를 모르는 상태일 수 있다. 그래서 네트워크 실패, 외부 처리 성공, 응답 손실, 서버 재시도 중 어디에서 중복이 생기는지 나눠 확인한다.

### 확인 방법

- 요청마다 business key나 idempotency key가 있는지 본다.
- timeout, retry, 외부 API 응답 상태를 trace id로 잇는다.
- 같은 key 요청이 동시에 들어올 때 DB unique 제약이나 상태 전이가 중복 처리를 막는지 테스트한다.
- 실패 뒤 재시도해도 같은 결과로 수렴하는지 확인한다.

### 해결

같은 의도의 요청에는 같은 idempotency key를 썼다. 서버는 key, payload hash, 처리 상태를 저장하고, 이미 끝난 요청이면 저장해 둔 결과를 돌려줬다. 외부 API가 idempotency key를 지원하면 같은 key를 넘기고, 지원하지 않으면 내부 상태 전이와 unique 제약으로 중복 처리를 막았다.

### 한계

- 같은 key에 다른 payload가 들어오면 충돌 정책이 필요하다.
- 외부 API가 멱등 키를 지원하지 않으면 내부에서 보장할 수 있는 범위가 좁아진다.
- key 보관 기간이 짧으면 늦게 온 재시도를 막지 못한다.
- timeout 뒤 결과를 확인할 API가 없으면 보상 처리나 수동 확인 절차가 필요할 수 있다.

### 면접에서 말하기

> 외부 API timeout은 처리 실패가 아니라 결과를 모르는 상태로 봅니다. 재시도로 중복 처리가 생기지 않게 같은 의도의 요청에는 idempotency key를 붙이고, key와 payload hash, 처리 상태를 저장합니다. 완료된 key가 다시 오면 같은 결과를 돌려주고, payload가 다르면 충돌로 처리합니다. 외부 시스템이 같은 보장을 해 주지 않으면 내부 상태 전이와 unique 제약으로 최소한의 중복을 막습니다.

## 사례 4: 배치 안정화

### 문제

주기적으로 도는 배치가 중간에 실패하면 어떤 데이터까지 처리됐는지 알기 어려웠다. 다시 돌리면 일부 데이터가 중복 처리될 수 있고, 안 돌리면 누락 데이터가 남았다.

### 원인 가설

배치 안정성 문제는 스케줄러보다 처리 단위와 재처리 기준에서 시작한다. 실패 시점, 처리 완료 표시, 중복 실행 가능성, 작업별 멱등성을 확인한다.

### 확인 방법

- 작업 단위별 상태가 `pending`, `processing`, `completed`, `failed`처럼 남는지 본다.
- 배치 실행 id, 처리 건수, 실패 건수, 마지막 처리 위치를 로그와 메트릭으로 남긴다.
- 같은 작업을 두 번 실행해도 결과가 깨지지 않는지 테스트한다.
- 이전 실행이 끝나기 전에 다음 실행이 시작되는지 확인한다.

### 해결

큰 작업을 chunk 단위로 나누고, chunk나 대상 row마다 처리 상태를 저장했다. 중복 실행이 위험한 작업은 lock이나 scheduler의 concurrency policy로 겹치지 않게 했다. 실패한 작업은 실패 사유와 재시도 가능 여부를 남기고, 재처리 대상은 `failed` 상태이거나 특정 기준 이후의 데이터로만 제한했다.

### 한계

- 상태 테이블과 재처리 로직이 생겨 구현이 복잡해진다.
- 외부 API 호출이 끼면 내부 상태만으로는 정확한 결과를 알 수 없다.
- lock이 멱등성을 대신하지는 못한다.
- 처리 단위를 너무 작게 나누면 관리 비용이, 너무 크게 나누면 재처리 비용이 커진다.

### 면접에서 말하기

> 배치는 실패하지 않는 것보다 실패했을 때 어디서부터 다시 시작할 수 있는지가 먼저입니다. 처리 단위를 chunk로 나누고 단위마다 상태, 실행 id, 처리 건수, 실패 사유를 남깁니다. 다시 돌려도 결과가 깨지지 않게 멱등성을 설계하고, 중복 실행이 위험하면 lock이나 CronJob concurrency policy를 씁니다. 운영에서는 성공 여부만이 아니라 처리 건수, 실패 건수, 실행 시간을 알림 기준으로 봅니다.

## 사례 5: 배포 안정화

### 문제

새 버전을 배포한 뒤 일부 API 오류율이 올랐는데, 배포 자체는 성공으로 표시됐다. 코드 문제인지, 설정 문제인지, 새 Pod 준비 문제인지 가려내는 데 시간이 걸렸다.

### 원인 가설

배포가 제대로 됐는지는 pipeline 성공 여부만으로 알 수 없다. 새 버전 Pod의 readiness, 설정 주입, error rate, latency, rollback 가능성을 함께 확인한다.

### 확인 방법

- rollout status와 Pod event를 본다.
- 배포 전후 error rate, p95 latency, restart count, readiness failure를 비교한다.
- ConfigMap, Secret, image tag가 의도한 값인지 확인한다.
- rollback할 때 DB schema와 설정이 이전 버전과 호환되는지 검토한다.

### 해결

readiness probe를 기준으로 준비된 Pod만 트래픽을 받게 하고, rolling update 중에도 가용 Pod 수가 유지되게 설정했다. 배포 뒤 일정 시간 핵심 지표를 보고, 오류율이 기준을 넘으면 rollback하는 운영 절차를 만들었다. 설정 변경과 코드 변경은 되도록 따로 배포해 원인을 쉽게 찾게 했다.

### 한계

- rollback은 Pod template은 되돌리지만 DB migration이나 외부 상태 변경은 자동으로 되돌리지 못한다.
- readiness 기준이 틀리면 배포 전략이 있어도 장애를 막지 못한다.
- 지표 기준이 없으면 배포 성공을 자동으로 판단하기 어렵다.
- replica가 너무 적으면 rolling update 중 가용성을 지키기 어렵다.

### 면접에서 말하기

> 배포 성공은 pipeline이 끝난 것이 아니라 새 버전이 정상 지표를 유지하는 것까지 확인해야 합니다. Kubernetes에서는 rollout 상태, readiness, Pod event, error rate, latency를 같이 봅니다. 무중단에 가깝게 배포하려면 replica 수, readiness probe, rolling update 전략이 맞아야 합니다. rollback은 준비해 두되, DB 변경이나 외부 상태 변경이 있으면 이전 버전과의 호환성을 먼저 설계합니다.

## 사례 6: 로그/알림 개선

### 문제

장애가 나면 사용자의 요청 흐름을 따라가기 어려웠다. 로그는 많았지만 어떤 요청에서 어떤 외부 호출과 DB 작업이 이어졌는지 연결되지 않았다. 알림은 늦거나 너무 많이 왔다.

### 원인 가설

관측성 문제는 로그 양이 모자라서가 아니라, 질문에 답할 신호가 없어서일 수 있다. 장애 분석에 필요한 trace id, 핵심 상태 변화 로그, 지표, 알림 기준이 있는지 확인한다.

### 확인 방법

- 요청 시작부터 외부 API, DB, 비동기 처리까지 같은 trace id가 전달되는지 본다.
- 오류 로그에 사용자를 식별할 수 있는 민감 정보 없이 원인 분류가 남는지 본다.
- latency, error rate, saturation 지표가 endpoint나 dependency 단위로 있는지 확인한다.
- 알림이 SLO나 사용자 영향과 이어지는지 확인한다.

### 해결

요청 단위 trace id와 correlation id를 표준화하고, 외부 API 호출과 비동기 메시지에도 넘겼다. 로그는 모든 값을 남기지 않고 상태 전이, 실패 사유, dependency, elapsed time 위주로 정리했다. 알림은 단순 error count 대신 오류율, p95 latency, 주요 batch 실패처럼 받으면 바로 움직일 수 있는 조건으로 바꿨다.

### 한계

- 로그를 늘리면 비용과 노이즈가 늘어난다.
- trace id가 한 경계에서라도 전달되지 않으면 흐름이 끊긴다.
- 알림 기준이 낮으면 피로가 쌓이고, 높으면 감지가 늦어진다.
- 민감 정보 마스킹 없이 로그를 늘리면 보안 위험이 커진다.

### 면접에서 말하기

> 장애 분석을 빠르게 하려면 로그 양보다 서로 이어지는 신호가 필요합니다. 요청마다 trace id를 붙이고 외부 API와 비동기 처리까지 넘겨 흐름을 잇습니다. 로그는 상태 변화, 실패 사유, dependency, elapsed time 위주로 남기고 민감 정보는 뺍니다. 알림은 로그 개수가 아니라 사용자 영향과 이어지는 오류율, 지연 시간, 실패율로 잡습니다.
