# Test Fixture

Test Fixture는 테스트 실행에 필요한 객체, DB 데이터, 외부 응답을 준비하는 데이터와 구성이다.

fixture는 테스트의 전제 조건이다. 좋은 fixture는 짧고, 검증하려는 조건만 드러낸다. fixture가 복잡하면 테스트가 무엇을 검증하는지 보이지 않는다.

## 상황별 선택

| 상황 | 선택 |
|---|---|
| 단순 값 객체 | 테스트 안에서 직접 생성 |
| 반복되는 도메인 객체 | Test Data Builder |
| DB 상태 필요 | 테스트별 명시적 setup |
| 복잡한 시나리오 | 의미 있는 factory 메서드 |

공유 fixture와 builder는 중복을 줄여 준다. 대신 공유 fixture는 테스트끼리 엮이게 만들고, builder를 지나치게 범용으로 만들면 기본값이 숨는다.

## 자주 깨지는 곳

- **거대한 fixture 하나를 여러 테스트가 공유한다.** 실행 순서에 따라 테스트가 깨진다.
- **테스트에 필요 없는 필드까지 다 드러낸다.** 어떤 값이 중요한지 안 보인다.
- **fixture 기본값이 도메인 규칙을 어긴다.** 실제로는 불가능한 상태를 검증하게 되어 테스트를 믿을 수 없다.
- **랜덤 데이터를 쓴다.** 실패했을 때 원인을 알기 어렵다.

## 점검할 것

- 테스트 이름과 fixture만 보고 조건을 이해할 수 있는지 본다.
- 테스트 실행 순서를 바꿔도 통과하는지 본다.
- fixture가 실제 도메인 invariant를 지키는지 확인한다.

## 면접에서 말하기

> Fixture는 테스트의 전제 조건을 표현하는 것이라, 저는 검증하려는 조건만 드러나게 짧게 씁니다. 반복되는 도메인 객체는 Test Data Builder로 만들되 숨겨진 기본값이 도메인 규칙을 어기지 않는지 확인합니다. 테스트끼리 데이터를 공유하면 순서에 따라 깨지기 때문에 DB 상태는 테스트마다 명시적으로 준비합니다.

## 꼬리 질문

- 테스트 fixture가 복잡하면 어떤 문제가 생기나?
- Test Data Builder는 언제 유용한가?
- 테스트 데이터 공유는 왜 위험한가?
