# Mock, Stub, Fake

Mock, Stub, Fake는 테스트에서 실제 의존성을 대신하는 객체다. Stub은 고정 응답을 주고, Mock은 호출이 일어났는지 검증하고, Fake는 단순한 구현체를 제공한다.

대역은 외부 API 실패, timeout, retry처럼 실제로는 재현하기 어려운 경계 상황을 만들 때 쓴다. 대신 쓸수록 실제 동작과 멀어진다. 모든 의존성을 mock으로 바꾸면 테스트는 통과하는데 운영에서는 깨진다.

## 무엇을 언제 쓰나

| 대역 | 사용 상황 |
|---|---|
| Stub | 특정 입력에 고정 응답이 필요할 때 |
| Mock | 특정 호출이 발생해야 하는지 검증할 때 |
| Fake | 메모리 저장소처럼 단순 동작 구현이 필요할 때 |
| Spy | 실제 객체 일부 동작을 관찰할 때 |

상호작용 검증(Mock)은 호출 자체가 요구사항일 때만 쓴다. 과하면 리팩터링 때마다 테스트가 깨진다. Fake는 단순한 실제 구현이지만 실제 인프라와 다르다. DB, transaction, lock 같은 동작은 fake나 mock으로는 부족하다.

## 자주 깨지는 곳

- **결과 대신 메서드 호출 여부만 검증한다.** 동작이 맞는지는 모른 채 구현을 그대로 따라 쓴 테스트가 된다.
- **private 구현에 가까운 호출 순서를 테스트한다.** 동작은 그대로인데 리팩터링만 해도 깨진다.
- **DB 동작을 fake repository로만 검증한다.** fake가 실제 저장소와 많이 다르면 잘못된 안심을 준다.
- **mock 설정이 테스트 본문보다 길다.** 테스트가 무엇을 검증하는지 안 보인다.

## 점검할 것

- 테스트가 행위 결과를 검증하는지, 구현 세부를 검증하는지 본다.
- mock을 빼도 단위 로직을 검증할 수 있는지 본다.
- fake와 실제 구현의 차이가 중요한 위험을 가리지 않는지 확인한다.

## 한 번에 설명하기

> 테스트 대역은 실제 의존성을 대신해 테스트 범위와 실패 조건을 제어하는 도구입니다. Stub은 응답을 주고 Mock은 상호작용을 검증하는데, 저는 호출 자체가 요구사항일 때만 Mock 검증을 씁니다. Fake는 실제 인프라와 다르기 때문에 DB, 트랜잭션, lock처럼 인프라 동작이 중요한 부분은 실제 DB로 통합 테스트합니다.
