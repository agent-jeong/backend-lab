# Mock, Stub, Fake

Mock, Stub, Fake는 테스트에서 실제 의존성 자리에 대신 끼워 넣는 객체다. Stub은 정해 둔 응답을 돌려주고, Mock은 어떤 호출이 일어났는지 확인하고, Fake는 메모리 저장소처럼 간단하게 실제로 동작하는 구현이다.

결제 API가 timeout을 내거나 retry 끝에 실패하는 상황은 실제 환경에서 일부러 만들기 어렵다. 이럴 때 대역을 쓴다. 다만 대역을 쓸수록 테스트는 실제 동작과 멀어진다. 의존성을 전부 mock으로 바꾸면 테스트는 통과하는데 운영에서는 깨진다.

## 무엇을 언제 쓰나

| 대역 | 사용 상황 |
|---|---|
| Stub | 특정 입력에 고정 응답이 필요할 때 |
| Mock | 특정 호출이 발생해야 하는지 검증할 때 |
| Fake | 메모리 저장소처럼 단순 동작 구현이 필요할 때 |
| Spy | 실제 객체 일부 동작을 관찰할 때 |

호출이 일어났는지를 Mock으로 검사하는 건, 그 호출 자체가 요구사항일 때만 한다. 예를 들어 "주문이 끝나면 알림을 한 번 보낸다"가 요구사항이라면 호출 검사가 맞다. 이런 검사가 많아지면 리팩터링할 때마다 테스트가 깨진다. Fake는 간단한 실제 구현이지만 진짜 인프라와는 다르다. DB, transaction, lock 같은 동작은 fake나 mock으로 확인할 수 없다.

## 자주 깨지는 곳

- 결과 대신 메서드가 불렸는지만 검사하면, 동작이 맞는지는 모른 채 구현을 그대로 베낀 테스트가 된다.
- private 구현에 가까운 호출 순서를 테스트하면, 동작은 그대로인데 리팩터링만 해도 깨진다.
- DB 동작을 fake repository로만 확인하면, fake가 실제 저장소와 다른 부분에서 잘못된 안심을 준다.
- mock 설정이 테스트 본문보다 길면, 테스트가 무엇을 확인하는지 읽히지 않는다.

## 점검할 것

- 테스트가 동작의 결과를 확인하는지, 구현 세부를 확인하는지 본다.
- mock을 빼고도 단위 로직을 확인할 수 있는지 본다.
- fake와 실제 구현이 다른 부분이 중요한 위험을 가리고 있지 않은지 확인한다.

## 한 번에 설명하기

> 테스트 대역은 실제 의존성을 대신해서, 테스트 범위를 좁히고 실패 상황을 마음대로 만들 수 있게 해 주는 도구입니다.
>
> Stub은 응답을 주고 Mock은 호출이 일어났는지 확인하는데, Mock 검사는 그 호출 자체가 요구사항일 때만 씁니다.
>
> Fake는 실제 인프라와 다르게 동작하기 때문에, DB나 트랜잭션, lock처럼 인프라 동작이 중요한 부분은 실제 DB로 통합 테스트합니다.
