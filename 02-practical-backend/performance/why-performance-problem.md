# 성능 문제를 정의하는 기준

성능 문제는 그냥 느린 상태가 아니다. 정해 둔 사용량과 조건에서 응답 시간, 처리량, 오류율 목표를 못 맞추는 상태다.

"주문 조회가 느리다"는 말만으로는 무엇을 고쳐야 할지 모른다. 평균 응답 시간은 괜찮은데 p95/p99가 나쁘면, 일부 사용자는 이미 장애를 겪고 있다. 재현 조건 없이 튜닝하면 고치기 전과 후를 비교할 수 없고, 병목을 확인하지 않고 캐시나 인덱스, 스케일아웃부터 붙이면 다른 장애가 생긴다. 성능을 올리면 정합성, 비용, 복잡도 중 무언가를 내준다.

## 정의하는 순서

1. 사용자가 실제로 불편을 겪는 API나 작업을 고른다.
2. 목표 지표를 정한다.
3. 요청량, 데이터 크기, 동시 사용자 수, 외부 의존성을 고정한다.
4. 지금 지표를 잰다.
5. 병목을 좁힌 뒤 하나씩 고치고 다시 잰다.

```text
목표:
- 주문 조회 API p95 < 300ms
- error rate < 0.1%
- 1분 평균 300 RPS

재현 조건:
- 주문 100만 건
- 사용자별 최근 주문 20건 조회
- Redis cache cold/warm 상태를 분리 측정
```

고치기 전에 "무엇을 얼마나 빠르게 할지"와 "어떤 조건에서 잴지"를 먼저 적는다. 지표를 모으고 재현 환경을 만드는 데 품이 들고, 운영 트래픽의 변수를 다 통제할 수도 없다. 그래도 이걸 적어 두면 하지 않아도 될 튜닝이 줄어든다.

## 상황별로 먼저 볼 기준

| 상황 | 먼저 볼 기준 | 이유 |
|---|---|---|
| 사용자 API 지연 | p95/p99 latency | 일부 사용자 지연이 평균에 가려진다 |
| 대량 트래픽 처리 | throughput, error rate | 많이 처리해도 실패가 늘면 소용없다 |
| 배치 지연 | 처리 시간, 처리 건수, 재시작 가능성 | 사용자 API와 목표가 다르다 |
| 간헐적 timeout | dependency latency, pool usage | 외부 의존성과 자원 고갈을 같이 봐야 한다 |
| 개선 검증 | 개선 전후 같은 조건 | 조건이 다르면 비교할 수 없다 |

## 자주 깨지는 곳

- 평균 latency만 보고 괜찮다고 하면, p99에 걸린 사용자의 불편을 놓친다.
- 목표 지표 없이 "빠르게"만 노리면, 어디서 멈춰야 할지 모르고 튜닝이 끝나지 않는다.
- 병목을 확인하기 전에 캐시부터 붙이면, 느린 곳은 그대로인데 비용과 복잡도만 는다.
- 로컬에서 잰 결과를 운영 성능으로 믿으면, 데이터 크기와 트래픽이 다른 운영에서 다시 느려진다.
- 고친 뒤 오류율, DB 부하, 비용을 확인하지 않으면, 빨라진 대가로 다른 곳이 망가진 걸 늦게 안다.

## 운영에서 볼 것

- 같은 데이터 크기와 요청량으로 고치기 전과 후를 비교한다.
- request id, endpoint, elapsed time, dependency elapsed time을 로그로 남긴다.
- p50/p95/p99 latency, throughput, error rate, saturation을 본다.
- CPU, thread, DB query, external call 중 어디서 시간을 쓰는지 프로파일링한다.

## 한 번에 설명하기

> 성능 문제는 느리다는 느낌이 아니라 목표 지표를 못 맞추는 상태라고 봅니다.
>
> 그래서 먼저 p95/p99, error rate, saturation 같은 목표를 정하고, 요청량, 데이터 크기, 캐시 상태, 외부 의존성 같은 재현 조건을 고정합니다.
>
> 그다음 병목을 확인하고 하나씩 고친 뒤, 같은 조건에서 다시 재서 숫자로 비교합니다.
