# 성능 문제를 정의하는 기준

성능 문제는 그냥 느린 상태가 아니라, 정해진 사용량과 조건에서 응답 시간, 처리량, 오류율 같은 목표를 만족하지 못하는 상태다.

"느리다"만으로는 어떤 지표를 고쳐야 하는지 알 수 없다. 평균 응답 시간은 괜찮아도 p95/p99가 나쁘면 사용자 일부는 장애를 겪는다. 재현 조건 없이 튜닝하면 전후 비교가 안 되고, 병목을 확인하지 않고 캐시, 인덱스, 스케일아웃을 붙이면 다른 장애를 만든다. 성능 개선은 정합성, 비용, 복잡도와 늘 맞바꾸는 일이다.

## 정의하는 순서

1. 사용자 영향이 있는 API나 작업을 정한다.
2. 목표 지표를 정한다.
3. 요청량, 데이터 크기, 동시 사용자 수, 외부 의존성을 고정한다.
4. 현재 지표를 측정한다.
5. 병목을 좁힌 뒤 하나씩 개선하고 다시 측정한다.

```text
목표:
- 주문 조회 API p95 < 300ms
- error rate < 0.1%
- 1분 평균 300 RPS

재현 조건:
- 주문 100만 건
- 사용자별 최근 주문 20건 조회
- Redis cache cold/warm 상태를 분리 측정
```

개선 전에 "무엇을 얼마나 빠르게 할 것인지"와 "어떤 조건에서 측정할 것인지"를 먼저 적는다. 지표 수집 체계와 재현 환경을 만드는 데 비용이 들고 운영 트래픽의 모든 변수를 통제할 수는 없지만, 이 단계가 있어야 불필요한 튜닝을 줄인다.

## 상황별로 먼저 볼 기준

| 상황 | 먼저 볼 기준 | 이유 |
|---|---|---|
| 사용자 API 지연 | p95/p99 latency | 일부 사용자 지연이 평균에 가려진다 |
| 대량 트래픽 처리 | throughput, error rate | 많이 처리해도 실패가 늘면 의미가 없다 |
| 배치 지연 | 처리 시간, 처리 건수, 재시작 가능성 | 사용자 API와 목표가 다르다 |
| 간헐적 timeout | dependency latency, pool usage | 외부 의존성과 자원 고갈을 같이 봐야 한다 |
| 개선 검증 | 개선 전후 같은 조건 | 조건이 다르면 비교가 무의미하다 |

## 자주 깨지는 곳

- **평균 latency만 보고 괜찮다고 판단한다.**
- **목표 지표 없이 "빠르게"만 시도한다.**
- **병목을 확인하기 전에 캐시부터 붙인다.** 비용과 복잡도만 는다.
- **로컬 테스트 결과를 운영 성능으로 일반화한다.**
- **개선 후 오류율, DB 부하, 비용 증가를 확인하지 않는다.**

## 운영에서 볼 것

- 같은 데이터 크기와 요청량으로 개선 전후를 비교한다.
- request id, endpoint, elapsed time, dependency elapsed time을 로그로 남긴다.
- p50/p95/p99 latency, throughput, error rate, saturation을 본다.
- CPU, thread, DB query, external call 중 어디서 시간을 쓰는지 프로파일링한다.

## 면접에서 말하기

> 성능 문제는 느린 느낌이 아니라 목표 지표를 만족하지 못하는 상태라고 봅니다. 그래서 저는 먼저 p95/p99, error rate, saturation 같은 목표와, 요청량·데이터 크기·캐시 상태·외부 의존성 같은 재현 조건을 정합니다. 병목을 확인한 뒤 하나씩 개선하고, 개선 전후를 같은 조건에서 숫자로 비교해 증명합니다.
