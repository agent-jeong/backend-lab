# 실패 상태 관리

실패 상태 관리는 배치 작업의 성공, 실패, 재시도 가능 여부, 실패 사유를 기록해 두는 일이다. 이 기록은 로그가 아니라 다시 돌릴지, 손으로 보정할지를 정하는 판단 데이터다.

## 상태를 어떻게 나누나

성공/실패 boolean 하나로는 부족하다. 처리 상태와 실패 사유를 따로 둔다.

| 상태 | 의미 |
|---|---|
| pending | 아직 처리 전 |
| processing | 처리 중 |
| completed | 처리 완료 |
| failed_retryable | 재시도 가능 실패 |
| failed_final | 수동 확인 또는 보정 필요 |

상태와 함께 실패 사유, 재시도 횟수, 마지막 시도 시각을 남긴다. 재시도 횟수와 마지막 시도 시각이 있어야 같은 실패가 끝없이 반복되는 것을 끊을 수 있다.

## 자주 깨지는 곳

- **실패를 boolean 하나로만 저장한다.** 중복 처리와 누락 처리를 구분할 수 없다.
- **실패 사유와 stack trace를 남기지 않는다.** 재실행할지 수동 보정할지 판단할 근거가 없다.
- **processing에서 멈춘 작업을 복구할 기준이 없다.** 일정 시간이 지나면 멈춘 것으로 보는 timeout 기준이 필요하다.
- **재시도 횟수와 마지막 시도 시각을 남기지 않는다.** 재시도 상한이 없으면 같은 실패가 반복된다.
- **실패 알림에 처리 대상 정보가 없다.** 무엇이 실패했는지 찾느라 복구가 늦어진다.

## 운영에서 볼 것

- 운영자가 실패한 작업 목록과 실패 이유를 조회할 수 있는지 확인한다.
- 오래 머문 processing 상태를 감지할 수 있는지 확인한다.
- 재시도 횟수를 넘기면 final 실패로 바뀌는지 테스트한다.

## 면접에서 말하기

> 배치 실패 상태는 재처리를 판단하기 위한 데이터라고 봅니다. 그래서 성공/실패 boolean 대신 pending, processing, completed, 재시도 가능 실패, 최종 실패로 나누고 실패 사유를 같이 남깁니다. processing에서 멈춘 작업은 timeout 기준으로 복구하고, 재시도 횟수와 마지막 시도 시각으로 반복 실패를 끊습니다.

## 꼬리 질문

- 배치 상태는 어떤 값으로 나누나?
- processing에서 멈춘 작업은 어떻게 복구하나?
- 실패 사유는 어디까지 저장하나?
