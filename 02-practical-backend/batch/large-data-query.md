# 대용량 조회

배치의 대용량 조회는 많은 데이터를 메모리, DB 부하, 정렬 안정성, 재시작 가능성을 따져 나눠 읽는 일이다. 여기서는 빨리 읽는 것보다 빠짐없이, 두 번 읽지 않고 끝까지 도는 것이 먼저다.

## 상황별 선택

| 상황 | 선택 |
|---|---|
| 큰 목록 순차 처리 | keyset pagination |
| 정렬 기준 필요 | unique하고 증가하는 key |
| 읽기 전용 대량 처리 | stream/cursor 검토 |
| 재시작 필요 | 마지막 처리 key 저장 |

keyset 방식은 마지막으로 처리한 key 다음 범위를 읽는다. 그 key를 저장해 두면 실패 뒤 거기서부터 다시 시작할 수 있다. 정렬 기준은 안정적이어야 하고, 가능하면 unique해야 한다.

## 자주 깨지는 곳

- **전체 데이터를 한 번에 로딩한다.** OOM이 나거나 GC가 길어진다.
- **offset pagination으로 배치 전체를 처리한다.** 뒤 페이지로 갈수록 scan 비용이 커지고, 처리 중 데이터가 바뀌면 누락과 중복이 생긴다.
- **정렬 조건 없이 limit만 쓴다.** 정렬이 불안정하면 같은 데이터를 여러 번 읽거나 빠뜨린다.
- **`select *`로 필요 없는 컬럼까지 읽는다.**
- **count query 비용을 무시한다.**

## 확인하는 법

- 실행 계획에서 scan row, index 사용, filesort 여부를 본다.
- 처리 중 데이터가 추가·수정돼도 누락이 없는지 테스트한다.
- 메모리 사용량과 fetch size를 확인한다.

## 면접에서 말하기

> 배치에서 대용량을 읽을 때는 빠른 조회보다 끝까지 빠짐없이 도는 것이 먼저입니다. offset은 데이터가 많을수록 느려지고 처리 중 데이터가 바뀌면 누락이나 중복이 생겨서, 저는 unique한 key 기준 keyset으로 읽고 마지막 처리 key를 저장해 재시작 지점으로 씁니다. 필요한 컬럼만 읽고 실행 계획으로 비용을 확인합니다.
