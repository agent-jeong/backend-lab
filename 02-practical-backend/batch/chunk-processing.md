# Chunk 처리

Chunk 처리는 대량 데이터를 한 번에 다루지 않고, 정해진 크기 묶음으로 나눠 읽고, 처리하고, 저장하는 방식이다. 묶음마다 커밋하고 어디까지 했는지 남겨 두니, 실패해도 다시 할 범위가 작다.

주문 100만 건을 한 번에 읽으면 메모리를 많이 쓰고 트랜잭션도 길어진다. 큰 트랜잭션 하나는 lock을 오래 잡고, 끝 무렵에 실패하면 처음부터 다시 해야 한다.

## 상황별 선택

| 상황 | 선택 |
|---|---|
| 데이터가 매우 큼 | chunk 단위 처리 |
| 정렬 기준이 안정적 | keyset 기반 조회 |
| 실패 재처리 필요 | chunk별 상태 저장 |
| 외부 API 호출 포함 | 더 작은 chunk와 재시도 정책 |

chunk 크기는 처리량, 메모리, 외부 API 비용을 보고 정한다. 너무 작으면 커밋과 조회를 자주 해서 그 비용이 커지고, 너무 크면 한 번 실패할 때 다시 할 양이 커진다.

## 자주 깨지는 곳

- 처리하는 동안 바뀌는 데이터를 offset pagination으로 읽으면, 중간에 행이 추가되거나 삭제될 때 빠지거나 두 번 처리되는 행이 생긴다. 이런 데이터는 key 기준으로 읽는다.
- 전체 작업을 트랜잭션 하나로 묶으면, lock을 오래 잡고 실패하면 처음부터 다시 해야 한다.
- chunk를 처리하고 진행 상태를 남기지 않으면, 실패한 뒤 어디서부터 다시 할지 알 수 없다.
- chunk 크기를 재 보지 않고 감으로 정하면, 너무 작거나 너무 커서 생기는 문제를 운영에서 처음 만난다.

## 확인하는 법

- chunk 크기별로 처리 시간, 메모리, DB lock 시간을 비교한다.
- 실패했을 때 마지막으로 끝난 chunk 다음부터 재시작되는지 확인한다.
- 처리 중에 데이터가 바뀌어도 빠지거나 두 번 처리되는 행이 없는지 테스트한다.

## 한 번에 설명하기

> Chunk 처리는 대량 작업을 작은 묶음으로 나눠 묶음마다 커밋하는 방식입니다. 전체를 트랜잭션 하나로 묶으면 lock을 오래 잡고, 실패하면 처음부터 다시 해야 하기 때문입니다.
>
> chunk 크기는 처리량, 메모리, 외부 API 비용을 재 보고 정합니다. chunk마다 진행 상태를 남겨서 실패하면 그 지점부터 다시 돌립니다.
>
> 처리 중에 바뀌는 데이터는 offset 대신 key 기준으로 읽습니다.
