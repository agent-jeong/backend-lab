# Chunk 처리

Chunk 처리는 대량 데이터를 한 번에 처리하지 않고 일정 크기 묶음으로 나눠 읽고, 처리하고, 저장하는 방식이다. 묶음 단위로 커밋하고 진행 상태를 남기기 때문에 실패해도 다시 처리할 범위가 작아진다.

한 번에 읽으면 메모리 사용량과 트랜잭션 시간이 커진다. 큰 트랜잭션 하나는 lock을 오래 잡고, 실패하면 전부 다시 해야 한다.

## 상황별 선택

| 상황 | 선택 |
|---|---|
| 데이터가 매우 큼 | chunk 단위 처리 |
| 정렬 기준이 안정적 | keyset 기반 조회 |
| 실패 재처리 필요 | chunk별 상태 저장 |
| 외부 API 호출 포함 | 더 작은 chunk와 재시도 정책 |

chunk 크기는 처리량, 메모리, 외부 API 비용을 보고 정한다. 너무 작으면 커밋과 조회 오버헤드가 커지고, 너무 크면 장애 한 번의 영향이 커진다.

## 자주 깨지는 곳

- **변경 중인 데이터를 offset pagination으로 처리한다.** 처리하는 동안 행이 추가·삭제되면 누락이나 중복이 생긴다. 변경 중인 데이터는 key 기준으로 읽는다.
- **전체 작업을 트랜잭션 하나로 묶는다.** lock 유지 시간이 길고 실패하면 처음부터 다시 해야 한다.
- **chunk 처리 뒤 진행 상태를 남기지 않는다.** 실패 후 어디서부터 다시 할지 알 수 없다.
- **chunk 크기를 측정 없이 감으로 정한다.**

## 확인하는 법

- chunk 크기별로 처리 시간, 메모리, DB lock 시간을 비교한다.
- 실패했을 때 마지막으로 끝난 chunk 다음부터 재시작되는지 확인한다.
- 처리 중 데이터가 바뀌어도 누락·중복이 없는지 테스트한다.

## 면접에서 말하기

> Chunk 처리는 대량 작업을 작은 묶음으로 나눠 묶음마다 커밋하는 방식입니다. 전체를 큰 트랜잭션 하나로 묶으면 lock을 오래 잡고 실패 시 처음부터 다시 해야 하기 때문입니다. 저는 chunk 크기를 처리량, 메모리, 외부 API 비용을 측정해서 정하고, chunk마다 진행 상태를 남겨 실패 지점부터 재처리합니다. 처리 중에 바뀌는 데이터는 offset 대신 key 기준으로 읽습니다.
