# 재처리 설계

재처리 설계는 배치가 중간에 실패해도, 어디까지 끝났고 무엇이 실패했는지 보고 나머지만 다시 돌릴 수 있게 짜 두는 일이다. 장애가 난 뒤에 운영자가 방법을 궁리할 일이 아니라, 배치를 처음 만들 때 넣어야 한다.

이걸 빼먹으면 정산 배치가 실패할 때마다 처음부터 다시 돌리거나, DB를 손으로 고치고 임시 스크립트로 메우게 된다.

## 단위별 설계

| 상황 | 설계 |
|---|---|
| row 단위 작업 | 대상마다 처리 상태 저장 |
| chunk 단위 작업 | chunk checkpoint 저장 |
| 외부 호출 포함 | idempotency key와 결과 기록 |
| 실패 원인 분류 | retryable/non-retryable 구분 |

다시 돌 때 이미 끝난 작업은 건너뛰거나, 다시 해도 결과가 같아야 한다. 그렇지 않으면 알림이 두 번 가고, 정산이 두 번 되고, 상태가 두 번 바뀐다. 외부 API 호출이 끼어 있으면 우리 DB 상태만으로는 그 호출이 끝났는지 알 수 없다. 그래서 idempotency key를 쓰고 결과를 확인한다.

## 자주 깨지는 곳

- 배치 전체의 성공/실패만 기록하면, 어디서 실패했는지 몰라 처음부터 다시 돌려야 한다.
- 실패한 데이터를 다시 찾을 기준을 남기지 않으면, 재처리할 대상을 사람이 일일이 골라야 한다.
- 다시 돌려도 결과가 같은지 테스트하지 않으면, 실제 재실행 때 두 번 처리된 데이터를 처음 발견한다.
- 실패 사유 없이 `failed` 상태만 남기면, 다시 시도할 실패인지 사람이 봐야 할 실패인지 가를 수 없다.

## 확인하는 법

- 중간에 일부러 실패를 일으키고, 다시 돌린 결과를 확인한다.
- 같은 batch를 두 번 실행해도 결과가 깨지지 않는지 본다.
- 실패 사유, 재시도 횟수, 마지막 처리 시각이 남는지 확인한다.

## 한 번에 설명하기

> 다시 돌릴 수 있는 배치는 어디서 실패했는지와 대상마다 처리 상태를 남깁니다.
>
> 이미 끝난 작업은 건너뛰거나 다시 해도 결과가 같게 만들고, 실패는 다시 시도해도 되는 것과 안 되는 것으로 나눕니다. 외부 API가 끼면 idempotency key와 결과 기록으로 두 번 처리되는 걸 막습니다.
>
> 재처리는 장애 뒤에 궁리할 일이 아니라, 배치를 만들 때 같이 설계할 일로 봅니다.
