# 메시지 큐를 쓰는 이유와 대가

메시지 큐는 보내는 쪽과 받는 쪽 사이에 브로커를 두고, 일을 바로 시키는 대신 "이런 일이 있었다"는 메시지를 남겨 두는 방식이다. 받는 쪽은 자기 속도로 메시지를 꺼내 처리한다.

주문 완료 뒤에 알림 발송, 포인트 적립, 정산 데이터 적재를 붙인다고 해 보자. 주문 서비스가 셋을 차례로 호출하면 알림 서버 하나가 느려져도 주문 응답이 늦어지고, 포인트 서버가 죽으면 주문까지 실패한다. 메시지로 바꾸면 주문은 이벤트를 남기고 바로 끝난다. 대신 메시지가 두 번 오거나, 순서가 바뀌거나, DB에는 주문이 있는데 이벤트는 없는 상태를 직접 다뤄야 한다.

## 동기 호출과 메시지는 무엇이 다른가

동기 호출은 호출한 쪽이 결과를 받을 때까지 기다린다. 메시지는 브로커에 맡긴 순간 보낸 쪽 일이 끝난다.

| 구분 | 동기 호출 (HTTP 등) | 비동기 메시지 |
|---|---|---|
| 응답 시간 | 후속 작업 시간이 모두 더해진다 | 이벤트 저장까지만 기다린다 |
| 장애 전파 | 받는 쪽이 죽으면 보내는 쪽도 실패한다 | 받는 쪽이 죽어도 메시지는 브로커에 쌓인다 |
| 결과 확인 | 성공과 실패를 바로 안다 | 처리 결과는 나중에, 따로 확인한다 |
| 데이터 맞춤 | 호출이 끝나면 맞춰져 있다 | 소비자가 처리할 때까지 잠시 어긋난다 |
| 받는 쪽 추가 | 보내는 쪽 코드를 고친다 | 새 소비자를 붙이면 된다 |

그래서 사용자가 결과를 바로 알아야 하는 일은 동기로 남긴다. 결제 승인이나 재고 차감처럼 주문 성공 여부를 가르는 일이 그렇다. 주문이 끝난 뒤에 따라붙는 일, 늦어도 되는 일, 받는 쪽이 여럿인 일을 메시지로 뺀다.

## 전달 방식 세 가지

메시지 시스템은 장애가 났을 때 메시지를 어떻게 다루느냐에 따라 세 가지로 나뉜다.

- at-most-once는 메시지를 잃을 수는 있어도 두 번 주지는 않는다. 소비자가 처리 전에 "받았다"고 먼저 알리면 이렇게 된다.
- at-least-once는 메시지를 잃지 않는 대신 두 번 줄 수 있다. 처리를 끝낸 뒤 ack를 보내기 전에 소비자가 죽으면 같은 메시지가 다시 온다.
- exactly-once는 한 번만 처리한 것처럼 결과가 남는다. 다만 브로커가 이걸 해 주는 범위는 좁다.

실무에서는 대부분 at-least-once를 쓴다. 메시지를 잃으면 어떤 메시지가 사라졌는지조차 모르지만, 중복은 소비자가 막을 수 있기 때문이다. Kafka가 말하는 exactly-once도 Kafka 토픽에서 읽고 Kafka 토픽에 쓰는 범위에서만 성립한다. 소비자가 DB에 쓰거나 외부 API를 부르는 일까지 한 번으로 만들어 주지 않는다. 결국 소비자는 같은 메시지가 여러 번 온다고 보고 만든다. 방법은 [[message-consumer-idempotency|메시지 소비 멱등성]]에 있다.

## 순서는 어디까지 지켜지나

순서는 브로커 전체가 아니라 한 줄 안에서만 지켜진다. Kafka에서는 파티션 하나, RabbitMQ에서는 큐 하나가 그 한 줄이다.

같은 주문의 "결제 완료"와 "주문 취소"가 다른 파티션으로 가면 소비자가 취소를 먼저 처리할 수 있다. 그래서 순서가 필요한 이벤트는 주문 id 같은 키로 같은 줄에 모은다. 줄 하나를 소비자 여럿이 나눠 가져가거나, 실패한 메시지를 뒤로 미뤄 재시도하면 그 줄 안에서도 순서가 바뀐다.

순서를 브로커에만 맡기지 않는 방법도 있다. 이벤트에 버전이나 발생 시각을 담고, 소비자가 이미 더 최신 상태를 반영했다면 오래된 이벤트를 버리게 만든다. 상태 전이 규칙으로 "취소된 주문은 결제 완료로 바꾸지 않는다"를 걸어 두는 것도 같은 효과를 낸다.

## 재시도와 DLQ

처리에 실패한 메시지는 다시 시도하되, 횟수를 정해 두고 넘으면 DLQ(dead letter queue)로 보낸다.

실패에는 두 종류가 있다. 상대 서버가 잠깐 죽은 것처럼 다시 하면 성공하는 실패가 있고, 필수 필드가 빠진 메시지처럼 몇 번을 해도 실패하는 실패가 있다. 뒤쪽을 무한히 재시도하면 그 메시지가 줄을 막고, 같은 줄의 뒤 메시지가 모두 멈춘다. 그래서 재시도는 간격을 늘려 가며 몇 번만 하고, 그래도 안 되면 DLQ로 옮겨 줄을 비운다.

RabbitMQ는 소비자가 requeue 없이 거절한 메시지, TTL이 지난 메시지, 큐 길이 제한을 넘은 메시지, quorum queue의 재전달 한도를 넘은 메시지를 dead letter exchange로 보낸다. Kafka의 일반 consumer group에서는 브로커가 이 일을 하지 않는다. 그래서 Spring Kafka 같은 소비자 쪽 라이브러리가 실패한 레코드를 별도 토픽에 다시 쓴다.

DLQ는 버리는 곳이 아니라 사람이 확인하는 곳이다. 누가 보고, 원인을 고친 뒤 어떻게 다시 넣을지까지 정해 둔다.

## DB 저장과 메시지 발행을 같이 맞추기

주문을 DB에 저장하는 일과 브로커에 이벤트를 보내는 일은 하나의 트랜잭션으로 묶이지 않는다. 그래서 둘 중 하나만 일어나는 순간이 생긴다.

```java
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();
    kafkaTemplate.send("order-completed", order.getId().toString(), toEvent(order));
    // 여기서 commit이 실패하면 이벤트는 이미 나갔다
}
```

트랜잭션 안에서 보내면 commit이 실패했을 때 없는 주문의 이벤트가 나간다. commit 뒤에 보내면 그 사이에 서버가 죽었을 때 주문은 있는데 이벤트는 없다. 이 틈을 메우는 방법이 Outbox다. 주문 변경과 "보낼 이벤트" 행을 같은 트랜잭션에 저장하고, 발행은 따로 도는 publisher가 맡는다. 이벤트는 사라지지 않지만 두 번 나갈 수 있어서, 여기서도 소비자 멱등성이 따라온다. 자세한 흐름은 [[compensation-and-outbox|보상 트랜잭션과 Outbox]]에 있다.

## 큐 방식과 로그 방식

브로커는 메시지를 처리한 뒤 지우느냐, 남겨 두느냐로 크게 갈린다.

| 구분 | 큐 방식 (RabbitMQ classic, quorum queue) | 로그 방식 (Kafka) |
|---|---|---|
| 소비 후 메시지 | ack를 받으면 큐에서 지운다 | 보관 기간 동안 남는다. 소비와 무관하다 |
| 소비 위치 관리 | 브로커가 메시지별 ack로 관리한다 | 소비자 그룹이 파티션별 offset을 커밋한다 |
| 여러 소비자에게 전달 | 소비자마다 큐를 따로 묶는다 | 소비자 그룹을 하나 더 만든다 |
| 다시 읽기 | 지운 메시지는 다시 못 읽는다 | offset을 되돌려 다시 읽는다 |
| 라우팅 | exchange와 binding으로 규칙을 건다 | topic과 key로 나눈다 |
| 잘 맞는 일 | 작업 분배, 요청별 라우팅, 메시지별 재시도 | 이벤트 기록, 여러 시스템의 독립 소비, 재처리 |

작업 하나를 일꾼 여럿에게 나눠 주고 끝나면 지우는 일이라면 큐 방식이 단순하다. 주문 이벤트 하나를 알림, 포인트, 정산이 각자 읽고, 버그를 고친 뒤 지난 이벤트를 다시 처리해야 한다면 로그 방식이 맞다. RabbitMQ도 stream이라는 로그 방식 큐를 따로 제공하니, 제품 이름보다 소비 후 지우는지 여부로 고른다. Kafka의 동작은 [[kafka-core-concepts|Kafka 핵심 동작]]에서 이어서 다룬다.

## 자주 깨지는 곳

- 메시지가 정확히 한 번 온다고 믿으면, 재전달된 메시지로 포인트가 두 번 쌓인다.
- 사용자가 결과를 바로 알아야 하는 일을 메시지로 빼면, 화면에는 성공이 떴는데 실제 처리는 실패한 주문이 생긴다.
- 트랜잭션 안에서 메시지를 보내면, rollback된 주문의 이벤트가 이미 다른 서비스에 가 있다.
- 순서가 필요한 이벤트에 키를 주지 않으면, 같은 주문의 이벤트가 다른 줄로 흩어져 취소가 결제보다 먼저 처리된다.
- 재시도 횟수에 상한을 두지 않으면, 처리할 수 없는 메시지 하나가 뒤의 메시지를 모두 붙잡는다.
- DLQ를 만들어만 두고 보는 사람이 없으면, 실패한 정산 이벤트가 몇 주 뒤에야 발견된다.
- 이벤트에 전체 상태 대신 "변경분"만 담으면, 중간 이벤트 하나가 빠졌을 때 소비자가 틀린 값을 쌓아 간다.

## 운영에서 볼 것

- 소비 지연. 쌓인 메시지 수와 가장 오래된 메시지의 나이를 같이 본다. Kafka에서는 consumer lag이다.
- 재시도 횟수와 DLQ에 들어온 건수. DLQ가 0이 아닌 상태가 오래가면 알림을 건다.
- 처리 로그에 event id, 주문 id 같은 업무 키, 소비자 이름, 재전달 여부를 남긴다.
- Outbox를 쓰면 발행 대기 건수와 가장 오래 기다린 이벤트의 나이를 본다.

## 한 번에 설명하기

> 메시지 큐는 후속 작업을 주문 응답에서 떼어 내서, 한 서비스의 장애가 다른 서비스로 번지지 않게 하려고 씁니다. 주문 완료 뒤 알림, 포인트, 정산처럼 늦어도 되고 받는 쪽이 여럿인 일을 메시지로 뺍니다.
>
> 대가는 세 가지입니다. 같은 메시지가 두 번 올 수 있고, 순서는 파티션이나 큐 하나 안에서만 지켜지고, DB 저장과 발행이 따로 일어납니다.
>
> 그래서 저는 at-least-once를 전제로 소비자를 멱등하게 만들고, 순서가 필요한 이벤트는 같은 키로 묶고, 발행은 Outbox로 DB 트랜잭션과 맞춥니다. 재시도에는 상한을 두고 넘으면 DLQ로 보내서 사람이 확인합니다.

## 꼬리 질문

> [!question]- 모든 후속 처리를 메시지로 빼면 안 되나요?
> 사용자가 결과를 바로 알아야 하는 일은 동기로 둡니다. 결제 승인처럼 주문 성공 여부를 가르는 일을 메시지로 빼면, 응답은 성공인데 실제로는 실패한 주문이 생기고 그걸 사용자에게 다시 알릴 방법을 따로 만들어야 합니다.

> [!question]- exactly-once를 지원하는 브로커를 쓰면 소비자 멱등성은 필요 없나요?
> 필요합니다. Kafka의 exactly-once는 Kafka에서 읽고 Kafka에 쓰는 범위에서 성립합니다. 소비자가 DB에 쓰거나 외부 API를 부르는 일은 그 범위 밖이라, 처리 뒤 offset 커밋 전에 죽으면 같은 메시지를 다시 처리합니다.

> [!question]- 메시지 순서가 바뀌면 어떻게 막나요?
> 같은 주문의 이벤트는 주문 id를 키로 보내서 같은 파티션에 모읍니다. 그래도 재시도로 순서가 바뀔 수 있어서, 이벤트에 버전을 담고 소비자가 이미 더 최신 버전을 반영했다면 오래된 이벤트를 버리게 합니다.

> [!question]- DLQ에 들어간 메시지는 어떻게 처리하나요?
> 원인부터 봅니다. 상대 서버 장애였다면 복구 뒤 원래 토픽이나 큐로 다시 넣고, 메시지 형식 문제였다면 코드를 고치거나 데이터를 보정한 뒤 넣습니다. 다시 넣을 때도 소비자가 멱등해야 이미 일부 처리된 메시지가 두 번 반영되지 않습니다.

> [!question]- RabbitMQ와 Kafka 중 무엇을 고르나요?
> 메시지를 처리한 뒤 지워도 되는지로 고릅니다. 작업을 일꾼들에게 나눠 주고 끝내는 일이면 큐 방식이 단순하고, 같은 이벤트를 여러 시스템이 따로 읽거나 지난 이벤트를 다시 처리해야 하면 로그 방식인 Kafka가 맞습니다.
