# 낙관적 락

낙관적 락은 데이터를 미리 잠그지 않는다. 대신 저장할 때 version 같은 값을 비교해서, 그사이 다른 트랜잭션이 먼저 바꿨는지 알아챈다.

비관적 락과 가장 다른 점은 충돌을 막지 않고 알아채기만 한다는 것이다. 상품 정보 수정처럼 충돌이 드문 곳에서는 기다리는 일이 없어서 유리하다. 대신 충돌이 났을 때 다시 시도할지, 사용자에게 알릴지는 애플리케이션이 정해야 한다.

## 동작

1. 엔티티를 조회할 때 현재 version도 같이 읽는다.
2. 데이터를 고친다.
3. 저장할 때 `where id = ? and version = ?` 조건으로 update한다.
4. 다른 트랜잭션이 먼저 고쳐서 version이 바뀌었으면 update가 실패한다.
5. 애플리케이션이 충돌 예외를 잡아 다시 시도하거나 충돌 응답을 돌려준다.

```java
@Entity
public class Product {
    @Id
    private Long id;

    @Version
    private Long version;

    private int stock;
}
```

JPA의 `@Version`을 붙이면 엔티티를 고칠 때 version 조건이 함께 붙는다. 충돌이 나면 최신 상태를 다시 읽고 정해 둔 횟수만큼만 다시 시도한다. 아니면 `409 Conflict` 같은 응답을 줘서 사용자가 최신 값을 다시 보게 한다.

## 언제 쓰나

| 상황 | 선택 | 이유 |
|---|---|---|
| 충돌이 드문 수정 | 낙관적 락 | 락 대기 없이 처리량을 유지한다 |
| 충돌 시 재시도 가능 | 낙관적 락 + retry | 실패 비용이 낮다 |
| 사용자 입력 수정 | 충돌 안내 | 자동 재시도가 의도치 않은 덮어쓰기를 만든다 |
| 경합이 높은 카운터 | 조건부 update 또는 비관적 락 | 낙관적 락 재시도가 폭증한다 |
| 공개 API 수정 요청 | 409 Conflict 응답 검토 | 클라이언트가 최신 상태를 다시 읽고 재시도하게 한다 |

## 자주 깨지는 곳

- 낙관적 락이 충돌을 알아서 해결해 준다고 생각하면, 실패한 쪽을 처리하는 코드가 빠진다. 같은 데이터를 동시에 고치면 한쪽은 그냥 실패하고, 그 실패를 어떻게 다룰지는 따로 만들어야 한다.
- 충돌 예외를 잡지 않으면 500 응답으로 끝나서 서버 장애처럼 보인다.
- 충돌이 잦은 기능에 쓰면, 재시도가 몰려 오히려 느려진다.
- version 없이 DTO로 바로 update하는 경로가 있으면, 그 경로에서는 동시 수정이 그대로 덮어써진다.
- 최신 상태를 다시 읽지 않고 같은 요청을 그대로 다시 보내면, 또 충돌하거나 낡은 값으로 덮어쓴다.
- 재시도 범위에 외부 API 같은 부작용이 들어 있으면, 다시 시도할 때마다 외부 호출도 다시 나간다.

## 운영에서 볼 것

- 같은 행을 동시에 고쳐서 version 충돌이 나는지 테스트한다.
- entity id, 이전 version, 충돌 예외, 재시도 횟수를 로그로 남긴다.
- 낙관적 락 실패 횟수와 재시도 성공 비율을 본다.
- 코드 리뷰에서 모든 update 경로가 version 조건을 거치는지 확인한다.

## 한 번에 설명하기

> 낙관적 락은 충돌을 막지 않고, 저장하는 순간에 알아챕니다. 충돌이 드문 곳에서는 기다리는 일이 없어서 유리합니다.
>
> 충돌이 나면 최신 상태를 다시 읽고 정해 둔 횟수만큼만 다시 시도하거나 409로 알립니다. 외부 API 호출은 재시도 범위에 넣지 않습니다.
>
> 경합이 심해서 재시도가 몰리면 조건부 update나 비관적 락으로 바꿉니다.
