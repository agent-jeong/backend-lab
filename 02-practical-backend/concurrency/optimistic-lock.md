# 낙관적 락

낙관적 락은 데이터를 미리 잠그지 않고, 저장할 때 version 같은 값을 비교해 그사이 다른 트랜잭션이 바꿨는지 감지하는 방식이다.

충돌을 막는 게 아니라 감지한다는 점이 핵심 차이다. 충돌이 드문 곳에서는 락 대기가 없어서 유리하지만, 충돌이 나면 재시도할지 사용자에게 알릴지는 애플리케이션이 정해야 한다.

## 동작

1. 엔티티를 조회할 때 현재 version도 함께 읽는다.
2. 데이터를 수정한다.
3. 저장 시 `where id = ? and version = ?` 조건으로 update한다.
4. 다른 트랜잭션이 먼저 수정해 version이 바뀌었으면 update가 실패한다.
5. 애플리케이션은 충돌 예외를 잡아 재시도하거나 충돌 응답을 반환한다.

```java
@Entity
public class Product {
    @Id
    private Long id;

    @Version
    private Long version;

    private int stock;
}
```

JPA의 `@Version`은 엔티티를 수정할 때 version 조건을 붙여 동시 변경을 감지한다. 충돌이 나면 최신 상태를 다시 읽고 제한된 횟수만 재시도하거나, 사용자가 최신 값을 다시 확인하도록 `409 Conflict` 같은 응답을 준다.

## 언제 쓰나

| 상황 | 선택 | 이유 |
|---|---|---|
| 충돌이 드문 수정 | 낙관적 락 | 락 대기 없이 처리량을 유지한다 |
| 충돌 시 재시도 가능 | 낙관적 락 + retry | 실패 비용이 낮다 |
| 사용자 입력 수정 | 충돌 안내 | 자동 재시도가 의도치 않은 덮어쓰기를 만든다 |
| 경합이 높은 카운터 | 조건부 update 또는 비관적 락 | 낙관적 락 재시도가 폭증한다 |
| 공개 API 수정 요청 | 409 Conflict 응답 검토 | 클라이언트가 최신 상태를 다시 읽고 재시도하게 한다 |

## 자주 깨지는 곳

- **충돌을 자동으로 해결해 준다고 생각한다.** 같은 데이터를 동시에 고치면 한쪽은 실패할 뿐이다. 실패를 어떻게 처리할지는 따로 설계해야 한다.
- **충돌 예외를 잡지 않는다.** 500 응답으로 끝나 일반 서버 장애처럼 보인다.
- **충돌이 많은 기능에 쓴다.** 재시도가 폭증해 오히려 느려진다.
- **version 없는 DTO update로 우회한다.** 그 경로에서는 동시 변경이 그대로 덮어써진다.
- **최신 상태를 다시 읽지 않고 같은 요청을 맹목적으로 재시도한다.**
- **재시도 범위에 외부 API나 부작용을 넣는다.** 재시도할 때마다 외부 호출도 반복된다.

## 운영에서 볼 것

- 같은 row를 동시에 수정해 version 충돌이 나는지 테스트한다.
- entity id, old version, 충돌 예외, retry count를 로그로 남긴다.
- optimistic lock failure count와 retry success ratio를 본다.
- 코드 리뷰에서 모든 update 경로가 version 조건을 거치는지 확인한다.

## 면접에서 말하기

> 낙관적 락은 충돌을 막지 않고 저장 시점에 감지합니다. 충돌이 드문 곳에서는 대기가 없어서 유리합니다. 충돌이 나면 최신 상태를 다시 읽고 제한된 횟수만 재시도하거나 409로 알리고, 외부 API 호출은 재시도 범위에 넣지 않습니다. 경합이 높아 재시도가 폭증하면 조건부 update나 비관적 락으로 바꿉니다.
