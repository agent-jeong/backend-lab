# CI와 CD

CI는 바뀐 코드를 자주 합치고 그때마다 자동으로 빌드와 테스트를 돌리는 일이다. CD는 그렇게 검사가 끝난 변경을 매번 같은 방식으로 배포하는 일이다.

CI가 약하면 누군가 깨뜨린 코드를 며칠 뒤에야 알게 되고, CD가 약하면 사람마다 배포 절차가 달라서 장애가 났을 때 되돌리는 데도 오래 걸린다. 그렇다고 테스트 없이 배포만 자동화하면 장애도 빠르게 배포된다. 빠른 배포보다 되돌릴 수 있는 배포가 먼저다.

## 단계별 질문

| 단계 | 질문 |
|---|---|
| CI | 이 변경이 빌드되고 테스트를 통과하는가? |
| CD | 같은 절차로 안전하게 배포하고 되돌릴 수 있는가? |
| 배포 후 검증 | 지표와 로그가 정상인가? |
| 승인 | 어떤 변경은 수동 승인이나 점검이 필요한가? |

pipeline이 초록불로 끝났다고 배포가 성공한 게 아니다. 배포 뒤 서비스 지표까지 정상이어야 성공이다.

## 자주 깨지는 곳

- CI/CD를 도구 이름으로만 알면, 무엇을 검사하고 무엇을 되돌릴지는 정하지 않은 채 파이프라인만 생긴다.
- 테스트가 들쭉날쭉한 상태에서 자동 배포를 켜면, 실패를 무시하는 습관이 생기고 진짜 실패도 그냥 흘러간다.
- 배포 후 지표 확인을 pipeline 밖 수동 작업으로 두면, 배포 성공과 서비스 정상을 헷갈려 문제를 늦게 발견한다.
- 롤백 절차 없이 배포 속도만 높이면, 잘못된 배포를 빨리 되돌릴 방법이 없다.

## 운영에서 볼 것

- pull request마다 build/test가 도는지 확인한다.
- main branch 기준으로 배포 artifact를 다시 만들어도 같은 결과가 나오는지 확인한다.
- 배포 실패와, 배포 뒤 오류율이 오르는 일을 따로 감지하는지 확인한다.

## 한 번에 설명하기

> CI는 변경을 자주 합치고 그때마다 검사하는 과정이고, CD는 검사가 끝난 변경을 매번 같은 방식으로 배포하는 과정입니다. 저는 자동화를 켜기 전에 테스트, 설정, 권한, 롤백 기준부터 갖춥니다.
>
> 배포 성공은 pipeline이 성공한 것이 아니라 배포 뒤 서비스 지표가 정상인 것까지로 봅니다. 그리고 빠른 배포보다 되돌릴 수 있는 배포를 먼저 챙깁니다.
