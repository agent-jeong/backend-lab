# Observability가 필요한 이유

Observability는 밖에서 볼 수 있는 신호만으로 시스템 내부 상태와 장애 원인을 짐작할 수 있게 해 두는 능력이다.

장애가 난 뒤 로그가 부족하면 원인을 추측하게 된다. API가 느린지, DB가 느린지, 외부 API가 느린지 가르지 못하면 복구도 늦다. Observability는 이 추측을 증거로 바꾸려고 미리 해 두는 준비다.

## 신호를 보는 순서

1. 서비스가 요청을 처리하며 로그, 메트릭, 트레이스를 남긴다.
2. 메트릭으로 이상 징후와 영향 범위를 빠르게 본다.
3. 트레이스로 요청이 어느 구간에서 느려졌는지 본다.
4. 로그로 구체적인 입력, 상태, 예외, 판단 근거를 본다.
5. 원인을 좁혀 조치하고, 재발을 막도록 계측과 알림을 보완한다.

```text
증상:
- 주문 생성 API p95 2초 초과

확인:
- 메트릭: error rate 정상, latency 증가
- 트레이스: 외부 결제 API 구간에서 1.7초 사용
- 로그: retry 2회 발생

판단:
- 애플리케이션 로직보다 외부 의존성 지연과 retry 정책을 먼저 확인한다.
```

## 질문별로 먼저 볼 신호

| 질문 | 먼저 볼 신호 | 이유 |
|---|---|---|
| 장애인가 | SLI, error rate, latency | 사용자 영향을 판단한다 |
| 어디가 느린가 | trace, dependency latency | 지연 구간을 나눈다 |
| 왜 실패했나 | error log, exception, event log | 실패 조건을 확인한다 |
| 얼마나 퍼졌나 | endpoint, region, instance metric | 영향 범위를 좁힌다 |
| 재발할 수 있나 | saturation, queue, retry metric | 구조적 원인을 확인한다 |

계측에는 설계와 운영 비용이 든다. 잘못 고른 지표는 잘못된 판단을 만들고, 지표가 많아도 의사결정에 연결되지 않으면 쓸모가 없다. 계측이 모든 문제를 자동으로 설명해 주지도 않는다.

## 자주 깨지는 곳

- **로그만 많이 남긴다.** 메트릭과 트레이스가 없으면 어디가 문제인지부터 막힌다.
- **평균 latency만 본다.** 일부 사용자가 겪는 큰 지연이 평균에 묻혀 장애 영향을 작게 본다.
- **모든 이벤트를 알림으로 만든다.** 알림 피로로 진짜 장애를 놓친다. 반대로 알림이 없으면 장애를 고객 문의로 알게 된다.
- **request id 없이 로그를 남긴다.** 한 요청의 흐름을 따라갈 수 없다.
- **장애 후 코드만 고치고 끝낸다.** 계측을 보완하지 않으면 분석이 개인 경험에 의존하고, 같은 문제가 반복된다.

## 운영에서 볼 것

- 장애 상황을 가정하고, 어떤 지표와 로그로 원인을 찾을지 미리 점검한다.
- 로그에 request id, endpoint, 사용자를 특정하지 않는 식별자, 예외 원인이 있는지 본다.
- 메트릭은 latency, traffic, error, saturation.
- 트레이스에서 DB, Redis, 외부 API, queue 구간 시간이 나뉘어 보이는지 확인한다.

## 면접에서 말하기

> Observability는 장애 원인을 추측하지 않고 증거로 좁히기 위한 준비입니다. 저는 메트릭으로 장애 여부와 영향 범위를 먼저 보고, 트레이스로 어느 구간이 느린지 나누고, 로그로 실패 조건을 확인합니다. 장애가 끝나면 코드 수정만 하지 않고, 이번에 부족했던 계측과 알림을 같이 보완합니다.
