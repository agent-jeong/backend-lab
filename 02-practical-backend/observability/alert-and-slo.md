# Alert와 SLO

Alert는 운영자가 조치해야 할 사용자 영향이나 위험을 알리는 신호다. SLO는 서비스가 지켜야 할 신뢰성 목표다.

알림은 "누군가 봐야 하는 정보"가 아니라 "누군가 행동해야 하는 신호"여야 한다. SLO가 없으면 어떤 지표가 얼마나 나빠져야 장애인지 합의할 수 없고, 그러면 알림 기준도 감으로 정하게 된다.

## 설계 순서

1. 사용자 관점의 SLI를 정한다.
2. 목표 수준인 SLO를 정한다.
3. SLO를 어길 가능성이 큰 상황에 알림 조건을 건다.
4. 알림에 영향 범위, 최근 변경, 대시보드, 대응 문서를 넣는다.
5. 장애 후 알림 정확도와 노이즈를 조정한다.

```text
알림 조건:
- checkout API 5xx rate > 2% for 5m
- checkout API p95 latency > 1s for 10m
- db_pool_pending > 0 for 3m
```

## 상황별 알림 기준

| 상황 | 알림 기준 | 이유 |
|---|---|---|
| API 장애 | 5xx rate, timeout rate | 사용자 실패와 직접 연결된다 |
| 지연 장애 | p95/p99 latency | 체감 지연을 반영한다 |
| 자원 고갈 | pool pending, queue depth | 장애 전조를 잡는다 |
| 배치 실패 | 처리 실패율, 지연 시간 | 사용자 API와 기준이 다르다 |
| 외부 API 장애 | dependency error/timeout | 의존성 문제를 분리한다 |

CPU나 메모리 같은 자원 지표만으로는 사용자 영향을 판단하기 어렵다. 사용자 영향 기준으로 알림을 걸면 장애 인지가 빨라지고 우선순위도 정하기 쉽다. 그래도 모든 장애를 미리 잡아 주지는 않는다.

## 자주 깨지는 곳

- **모든 WARN 로그를 알림으로 연결한다.** 알림이 너무 많으면 운영자가 진짜 장애를 놓친다.
- **CPU 80% 같은 단일 임계치만 쓴다.** 사용자 영향과 연결되지 않는 알림이 울린다.
- **알림에 무엇을 어떻게 확인할지 정보가 없다.** 알림만 울리고 대응 절차가 없으면 복구 시간이 줄지 않는다.
- **업무 시간과 야간 알림의 긴급도를 나누지 않는다.** 밤에 급하지 않은 알림으로 사람을 깨운다.
- **알림이 울린 뒤 실제 조치가 있었는지 돌아보지 않는다.** 알림이 늦었는지, 시끄러웠는지 고칠 기회를 놓친다.

## 운영에서 볼 것

- 장애 시나리오에서 알림이 정해 둔 시간 안에 울리는지 테스트한다.
- 알림 시간대의 error log와 배포 이력을 확인한다.
- 메트릭은 SLI, error budget, burn rate.
- 알림에서 바로 원인 후보를 볼 수 있는 대시보드로 이어지는지 확인한다.

## 면접에서 말하기

> 알림은 운영자가 조치해야 할 사용자 영향에 연결돼야 하고, SLO는 어느 수준의 신뢰성을 제공할지 정하는 기준입니다. 그래서 저는 CPU 같은 자원 지표보다 5xx rate나 p95 latency처럼 사용자가 겪는 지표로 알림을 겁니다. 알림에는 영향 범위, 원인 후보, 확인 링크, 대응 절차를 같이 넣고, 장애 후에는 알림이 늦거나 시끄럽지 않았는지 조정합니다.
