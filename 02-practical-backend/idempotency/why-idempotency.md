# 멱등성이 필요한 이유

멱등성은 같은 요청이 한 번 처리되든 여러 번 처리되든 최종 업무 결과가 같도록 만드는 설계 원칙이다.

"요청은 한 번만 온다"는 가정은 운영에서 깨진다. 사용자는 버튼을 여러 번 누르고, timeout 뒤 클라이언트나 서버가 재시도하고, 메시지 브로커는 장애와 재처리 과정에서 같은 메시지를 다시 보낸다. 이 중복이 결제, 쿠폰, 포인트, 재고 차감에 반영되면 금전 오류가 된다.

## 동작

1. 요청을 구분할 기준을 정한다.
2. 이미 처리된 요청인지 확인한다.
3. 처음 보는 요청이면 업무를 처리하고 결과를 저장한다.
4. 이미 처리된 요청이면 기존 결과를 반환하거나 no-op으로 끝낸다.
5. 실패와 timeout은 성공, 실패, 결과 불명 상태로 나눠 복구한다.

```java
public PaymentResponse approve(PaymentRequest request) {
    return idempotencyService.execute(
        request.idempotencyKey(),
        () -> paymentService.approve(request)
    );
}
```

같은 `idempotencyKey`로 들어온 요청은 결제 승인 로직을 다시 실행하지 않고, 저장된 처리 결과로 응답한다.

## 어디에 필요한가

| 상황 | 선택 | 이유 |
|---|---|---|
| 조회 API | 별도 멱등 설계가 거의 필요 없음 | 같은 조회는 상태를 바꾸지 않는다 |
| 생성/결제/차감 API | 멱등성 필수 | 중복 처리되면 업무 결과가 달라진다 |
| 외부 API 재시도 | 멱등키 사용 | timeout 후 중복 부작용을 막아야 한다 |
| 메시지 소비 | 처리 이력 저장 | at-least-once 전달에서는 중복 소비가 가능하다 |
| 단순 상태 변경 | 조건부 update | 이미 처리된 상태를 다시 처리하지 않는다 |

멱등성을 갖추면 재시도와 중복 클릭에 안전해지고 장애 복구가 단순해진다. 대가로 요청 식별 기준과 저장소, 보관 기간과 저장 비용을 정해야 하고, 이미 일어난 부작용을 자동으로 되돌려 주지는 않는다.

## lock과 멱등성은 다르다

| 구분 | lock | 멱등성 |
|---|---|---|
| 막는 것 | 같은 순간에 겹친 실행 | 이미 처리된 요청의 재실행 |
| 기준 | 지금 누가 자원을 쥐고 있는가 | 이 요청을 전에 처리했는가 |
| 시간차 재시도 | 막지 못한다. 첫 요청이 끝나 락이 풀린 뒤 온 재시도는 그대로 실행된다 | 저장된 결과를 반환하거나 no-op으로 끝낸다 |
| 필요한 저장소 | 락 저장소(DB row, Redis 등) | 처리 이력, idempotency key, unique 제약 |

예를 들어 결제 승인 요청이 timeout으로 끝나고 클라이언트가 5초 뒤 재시도한다. 첫 요청은 이미 끝나 락도 풀렸으니 lock은 두 번째 승인을 막지 못한다. 같은 key의 처리 결과가 남아 있어야 이중 결제를 막는다. 실무에서는 둘을 같이 쓴다. lock(또는 unique insert)으로 동시 실행을 줄 세우고, 처리 이력으로 재시도를 알아본다.

## 자주 깨지는 곳

- **멱등성을 HTTP 메서드 성질로만 이해한다.**
- **timeout을 실패로 단정하고 같은 결제 요청을 새로 보낸다.**
- **프론트엔드 버튼 비활성화만으로 중복을 막으려 한다.**
- **lock을 쓰면 멱등성이 필요 없다고 생각한다.** 위 표처럼 시간차 재시도는 못 막는다.
- **처리 결과를 저장하지 않는다.** 중복 요청에 같은 응답을 줄 수 없다.

## 운영에서 볼 것

- 같은 요청을 여러 번 보내도 row 수, 금액, 재고가 변하지 않는지 테스트한다.
- idempotency key, request id, 처리 상태, 기존 응답 반환 여부를 로그로 남긴다.
- duplicate request count, idempotency hit count, retry count를 본다.
- pending이나 result-unknown 상태가 오래 남지 않는지 본다.

## 면접에서 말하기

> 멱등성은 같은 요청이 여러 번 와도 최종 결과가 한 번 처리한 것과 같게 만드는 설계입니다. 중복 클릭, timeout 뒤 재시도, 메시지 재전달은 운영에서 실제로 일어납니다. lock은 동시에 겹친 실행만 막고 이미 처리된 요청은 알아보지 못하기 때문에, 저는 결제·쿠폰·포인트·재고처럼 상태를 바꾸는 기능에 처리 이력과 DB 제약을 둬서 다시 와도 같은 결과가 나오게 합니다.
