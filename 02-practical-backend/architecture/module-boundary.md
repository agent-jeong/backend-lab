# 모듈 경계

모듈 경계는 함께 바뀌는 코드와 따로 바뀌어야 하는 코드를 나누는 선이다. 경계가 강할수록 독립성은 높아지지만 경계를 넘는 DTO, 매핑, 설정 비용도 커진다.

## 무엇을 기준으로 나누나

| 기준 | 설명 |
|---|---|
| 변경 이유 | 같이 바뀌는 코드는 같은 모듈 후보다 |
| 데이터 소유권 | 같은 데이터를 책임지는 코드가 경계를 이룬다 |
| 의존 방향 | 경계를 정한 뒤 허용할 참조 방향을 정한다 |
| 배포 단위 | 독립 배포가 필요하면 더 강한 경계가 필요하다 |

모듈이 너무 크면 작은 변경도 전체 빌드와 테스트에 영향을 준다. 너무 잘게 나누면 경계 비용이 이득을 넘는다. 경계는 변경 영향으로 먼저 검증하고, 의존 방향은 그 경계를 지키는 규칙으로 둔다.

## 자주 깨지는 곳

- **패키지만 나누고 내부 구현은 서로 직접 참조한다.** 경계가 불명확하면 다른 모듈의 내부 Entity나 Repository를 그대로 쓰게 된다.
- **공통화를 너무 빨리 해서 업무 개념을 common에 넣는다.** 공통 모듈은 재사용보다 안정성과 의미가 먼저 검증돼야 한다.
- **모듈 분리를 마이크로서비스 분리와 같은 것으로 본다.** 모듈 분리는 배포 단위 분리가 아니다.
- **DB 테이블을 공유하면서 모듈이 독립적이라고 믿는다.** 데이터 소유권이 섞이면 트랜잭션과 정합성 책임이 모호해진다.

## 확인하는 법

- 모듈 간 import 방향과 순환 의존을 확인한다.
- 기능 하나를 바꿀 때 수정되는 모듈 수를 센다.
- 다른 모듈의 내부 Entity나 Repository를 직접 쓰는 곳을 찾는다.

## 면접에서 말하기

> 저는 모듈 경계를 변경 이유와 데이터 소유권으로 정합니다. 경계를 강하게 할수록 독립성은 올라가지만 통합 비용도 같이 늘어서, 실제로 한 기능을 바꿀 때 몇 개 모듈이 바뀌는지로 경계를 검증합니다. 그리고 모듈 분리는 배포 단위 분리와 같지 않다는 점, 업무 개념을 너무 일찍 common으로 옮기지 않는다는 점을 지킵니다.
