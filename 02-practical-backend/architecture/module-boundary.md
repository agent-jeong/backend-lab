# 모듈 경계

모듈 경계는 함께 바뀌는 코드와 따로 바뀌어야 하는 코드 사이에 긋는 선이다. 예를 들어 주문과 정산은 다른 이유로 바뀌니 다른 모듈에 두는 편이 낫다.

경계를 단단하게 그을수록 모듈끼리 서로 덜 흔들린다. 그 대신 경계를 넘나드는 DTO, 매핑 코드, 설정이 늘어난다.

## 무엇을 기준으로 나누나

| 기준 | 설명 |
|---|---|
| 변경 이유 | 같이 바뀌는 코드는 같은 모듈 후보다 |
| 데이터 소유권 | 같은 데이터를 책임지는 코드가 경계를 이룬다 |
| 의존 방향 | 경계를 정한 뒤 허용할 참조 방향을 정한다 |
| 배포 단위 | 독립 배포가 필요하면 더 강한 경계가 필요하다 |

모듈이 너무 크면 작은 변경 하나에도 전체를 빌드하고 테스트해야 한다. 너무 잘게 나누면 경계를 유지하는 비용이 얻는 것보다 커진다. 경계가 맞는지는 먼저 무엇을 고칠 때 어디까지 바뀌는지로 확인하고, 의존 방향은 그 경계를 지키는 규칙으로 둔다.

## 자주 깨지는 곳

- 패키지만 나누고 내부 구현은 서로 직접 참조하면, 경계가 흐려져 다른 모듈의 내부 Entity나 Repository를 그대로 가져다 쓰게 된다.
- 너무 일찍 공통화해서 업무 개념을 common에 넣으면, common이 업무 변경에 끌려다닌다. 공통 모듈에 넣기 전에 재사용 여부보다 잘 안 바뀌는지와 뜻이 분명한지를 먼저 확인한다.
- 모듈 분리를 마이크로서비스 분리와 같은 것으로 보면, 필요 없는 배포 분리까지 하게 된다. 모듈 분리는 배포 단위 분리가 아니다.
- DB 테이블을 같이 쓰면서 모듈이 독립적이라고 믿으면, 데이터를 누가 책임지는지 섞여서 트랜잭션과 정합성 책임이 애매해진다.

## 확인하는 법

- 모듈 간 import 방향과 순환 의존을 확인한다.
- 기능 하나를 바꿀 때 수정되는 모듈 수를 센다.
- 다른 모듈의 내부 Entity나 Repository를 직접 쓰는 곳을 찾는다.

## 한 번에 설명하기

> 모듈 경계는 바뀌는 이유와 데이터를 누가 맡는지를 보고 정합니다.
>
> 경계를 단단하게 할수록 모듈끼리 덜 흔들리지만 연결하는 비용도 같이 늘어서, 실제로 기능 하나를 바꿀 때 모듈이 몇 개나 바뀌는지로 경계가 맞는지 확인합니다.
>
> 모듈 분리가 배포 단위 분리와 같지 않다는 점, 업무 개념을 너무 일찍 common으로 옮기지 않는다는 점도 지킵니다.
