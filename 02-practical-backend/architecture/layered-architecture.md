# 계층형 아키텍처

Layered Architecture는 애플리케이션을 표현, 비즈니스, 데이터 접근 같은 계층으로 나누고, 계층마다 맡을 일과 참조할 수 있는 방향을 정해 두는 구조다.

계층을 나누는 것 자체가 목적은 아니다. API 응답 형식이 바뀔 때 주문 할인 규칙까지 고치지 않도록, 바뀌는 이유가 다른 코드를 떼어 놓는 게 목적이다.

## 계층별 책임

1. Controller는 요청과 응답을 변환하고, 인증된 사용자 정보를 넘긴다.
2. Service는 유스케이스 흐름을 짜고, 트랜잭션 경계를 정하고, 도메인 규칙을 엮는다.
3. Domain은 상태와 규칙을 표현한다.
4. Repository는 저장소에 접근하는 방법을 감춘다.
5. 의존성은 보통 바깥 계층에서 안쪽 계층으로만 흐르게 제한한다.

업무 규칙은 되도록 웹과 DB 세부사항에서 떨어뜨려 둔다.

## 변경이 어디에 머물러야 하나

| 변경 | 영향이 머물러야 할 곳 |
|---|---|
| API 형식 변경 | Controller/DTO |
| 업무 규칙 변경 | Service/Domain |
| 저장소 변경 | Repository 구현 |
| 어느 계층에 둘지 고민될 때 | 변경 이유가 같은 코드를 같은 계층에 둔다 |

## 자주 깨지는 곳

- Controller에 비즈니스 로직이 쌓이면, API를 바꿀 때 정책도 같이 흔들린다.
- 계층은 나눴는데 모든 로직을 Service에 몰아넣으면, Service 하나가 모든 변경 이유를 떠안는다.
- Repository에 업무 규칙이 들어가면, 메서드 이름에 정책이 담기고 데이터 접근과 도메인 판단이 섞인다.
- 의존 방향이 뒤섞이면, 테스트하기 어렵고 무엇을 고칠 때 어디까지 영향이 가는지 알기 어렵다.
- Entity를 응답으로 그대로 내보내면, 저장 모델이 그대로 API 형식이 된다.
- 계층이 많을수록 좋다고 여겨 단순 CRUD에도 계층을 겹겹이 두면, 코드를 이해하는 데만 시간이 들고 개발 속도가 떨어진다.

## 확인하는 법

- 코드 리뷰: 각 계층 코드가 어떤 이유로 바뀌는지 본다.
- 테스트: 핵심 업무 규칙을 웹/DB 없이 검증할 수 있는지 본다.
- 의존성: 하위 계층이 상위 계층 타입을 참조하지 않는지 확인한다.

## 한 번에 설명하기

> Layered Architecture는 계층을 나누는 것 자체보다 바뀌는 이유를 나누는 데 목적이 있습니다.
>
> Controller는 입출력 변환, Service는 유스케이스 흐름, Repository는 저장소 접근을 맡고, 업무 규칙은 웹과 DB에서 떨어뜨려 둡니다.
>
> 설계가 맞는지는 무엇을 고칠 때 어디까지 영향이 가는지, 웹과 DB 없이 테스트할 수 있는지로 확인하고, 단순한 기능에는 계층을 과하게 두지 않습니다.
