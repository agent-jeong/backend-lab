# 모놀리스와 마이크로서비스

모놀리스는 애플리케이션 전체를 한 번에 빌드하고 한 프로세스로 배포하는 구조다. 마이크로서비스는 주문, 결제, 재고 같은 업무를 각자 배포하는 서비스로 나누고 네트워크로 서로 부르는 구조다.

나누는 순간 주문 저장과 결제 승인은 같은 트랜잭션에 들어가지 못한다. 메서드 호출이던 것이 HTTP 호출이 되면서 타임아웃과 부분 실패가 생긴다. 그래서 "나누면 좋은가"가 아니라 "나눠서 얻는 것이 이 비용보다 큰가"를 먼저 묻는다.

## 같은 주문 흐름이 어떻게 달라지나

모놀리스에서는 주문 저장과 재고 차감이 한 트랜잭션으로 묶인다. 하나가 실패하면 둘 다 rollback된다.

```java
@Transactional
public Long placeOrder(PlaceOrderCommand command) {
    Order order = orderRepository.save(Order.create(command.userId(), command.items()));
    stockService.decrease(command.items());   // 같은 DB, 같은 트랜잭션
    return order.getId();
}
```

재고가 다른 서비스로 나가면 같은 흐름이 이렇게 바뀐다. 아래는 Spring Framework 6.1(Spring Boot 3.2)부터 쓸 수 있는 `RestClient` 기준이다.

```java
public Long placeOrder(PlaceOrderCommand command) {
    Order order = orderService.createPending(command);   // 주문 DB에만 commit
    try {
        stockClient.post()
                .uri("https://stock.example.com/reservations")
                .body(new ReserveStockRequest(order.getId(), command.items()))
                .retrieve()
                .toBodilessEntity();
        orderService.confirm(order.getId());
    } catch (RestClientException e) {
        orderService.markStockUnknown(order.getId());   // 재고가 잡혔는지 모른다
        throw e;
    }
    return order.getId();
}
```

타임아웃이 나면 재고 서비스가 예약을 했는지 안 했는지 주문 서비스는 모른다. 그래서 재시도해도 두 번 잡히지 않게 주문 ID로 멱등하게 만들고, 끝내 실패하면 예약을 되돌리는 보상 흐름을 둔다. 이 설계는 [[compensation-and-outbox]]와 [[idempotency-key]]에서 다룬다. 모놀리스에서 rollback 한 번이던 일이 서비스 둘 사이의 약속으로 바뀐다.

## 나누면 늘어나는 비용

| 비용 | 모놀리스 | 마이크로서비스 |
|---|---|---|
| 트랜잭션 | DB 트랜잭션 하나로 묶는다 | 서비스마다 따로 commit하고 보상이나 outbox로 맞춘다 |
| 실패 | 예외가 호출 스택을 타고 올라온다 | 타임아웃, 재시도, 부분 실패를 호출마다 처리한다 |
| 데이터 정합성 | 커밋 직후 모든 조회가 같은 값을 본다 | 이벤트가 도착하기 전까지 서비스마다 값이 다르다 |
| 조회 | JOIN 한 번 | 여러 서비스를 부르거나 데이터를 복제해 둔다 |
| 운영 | 배포 파이프라인, 모니터링이 하나 | 서비스마다 파이프라인, 설정, 알림, 버전 호환이 생긴다 |
| 장애 추적 | 스택 트레이스 하나 | trace ID로 여러 서비스 로그를 이어 붙인다 |

마지막 줄은 [[distributed-tracing]]이 없으면 해결되지 않는다. 주문 API가 3초 걸렸을 때 주문, 재고, 결제 중 어디서 시간이 걸렸는지 각 서비스 로그만으로는 알 수 없다.

Martin Fowler는 이 비용을 Microservice Premium이라고 불렀다. 시스템이 단순할 때는 이 비용이 생산성을 깎고, 모놀리스로 감당하기 어려울 만큼 복잡해진 뒤에야 나누는 쪽이 낫다고 봤다. 그가 쓴 MonolithFirst 글도 성공한 마이크로서비스 사례 대부분이 너무 커진 모놀리스를 쪼개면서 시작했다고 적는다.

## 데이터베이스를 서비스마다 나누는 문제

서비스를 나눠도 DB를 같이 쓰면 독립 배포가 되지 않는다. 주문 서비스가 재고 테이블 컬럼 이름에 기대고 있으면, 재고 서비스가 스키마를 바꿀 때 주문 서비스도 같이 배포해야 한다. 그래서 서비스마다 자기 데이터를 갖고, 다른 서비스는 API나 이벤트로만 그 데이터에 닿는다.

DB를 나누면 대가가 따른다.

- 주문 목록 화면에 상품명과 재고 상태를 같이 보여 주던 JOIN이 사라진다. 다른 서비스 API를 여러 번 부르거나, 필요한 값을 이벤트로 받아 내 DB에 복제해 둔다.
- 복제한 값은 늦게 맞는다. 상품명이 바뀐 직후 주문 목록에는 옛 이름이 잠깐 보인다.
- 여러 서비스 데이터를 모아 보는 정산이나 통계 쿼리는 별도 저장소로 모은다.

강하게 같이 맞아야 하는 데이터를 다른 서비스로 떼면 이 비용이 매번 터진다. 재고 차감과 주문 확정처럼 한 번이라도 어긋나면 안 되는 쌍은 같은 서비스에 두는 편이 싸다.

## 모듈러 모놀리스라는 중간 선택

모듈러 모놀리스는 배포는 하나로 하고, 코드 안에서 모듈 경계를 마이크로서비스만큼 엄격하게 지키는 구조다. 주문 모듈은 결제 모듈의 공개 API만 부르고, 내부 Entity나 Repository에는 손대지 않는다. 경계를 긋는 기준은 [[module-boundary]]와 같다.

Spring Modulith를 쓰면 이 경계를 테스트로 검사한다. 기본 설정에서는 `@SpringBootApplication` 클래스가 있는 패키지의 바로 아래 패키지 하나하나가 모듈이 된다.

```java
class ModuleStructureTest {

    @Test
    void verifiesModuleBoundaries() {
        ApplicationModules.of(ExampleApplication.class).verify();
    }
}
```

다른 모듈의 내부 패키지를 참조하거나 모듈 사이에 순환 의존이 생기면 `verify()`가 예외를 던져 테스트가 실패한다. 이렇게 경계를 지켜 두면 나중에 한 모듈을 서비스로 떼어 낼 때 끊을 곳이 이미 정해져 있다. 반대로 경계가 없는 모놀리스는 떼어 내려는 순간 어디가 어디를 부르는지부터 조사해야 한다.

## 서비스 경계를 정하는 기준

| 기준 | 같은 서비스에 둔다 | 다른 서비스로 뗀다 |
|---|---|---|
| 정합성 | 한 트랜잭션에서 같이 맞아야 한다 | 몇 초 늦게 맞아도 업무가 버틴다 |
| 변경 이유 | 같은 요구사항 때문에 같이 바뀐다 | 다른 정책, 다른 주기로 바뀐다 |
| 팀 | 한 팀이 맡는다 | 다른 팀이 따로 배포 일정을 잡는다 |
| 부하 | 같이 늘고 같이 준다 | 한쪽만 트래픽이 몰려 따로 늘려야 한다 |
| 장애 | 같이 죽어도 업무 영향이 비슷하다 | 한쪽 장애가 다른 쪽으로 번지면 안 된다 |

팀 경계가 들어가는 이유는 조직 구조가 시스템 구조를 닮는다는 Conway의 법칙 때문이다. 한 팀이 서비스 다섯 개를 맡으면 배포만 다섯 번으로 늘고 독립 배포로 얻는 것은 적다.

## 언제 무엇을 쓰나

| 상황 | 선택 | 이유 |
|---|---|---|
| 팀 하나, 업무 경계가 아직 흔들린다 | 모놀리스 | 경계를 잘못 그어도 리팩터링으로 옮긴다 |
| 팀이 여럿이고 배포가 서로 막는다 | 모듈러 모놀리스부터 | 배포 비용 없이 코드 경계를 먼저 확인한다 |
| 한 모듈만 부하나 배포 주기가 확연히 다르다 | 그 모듈만 서비스로 뗀다 | 나누는 비용을 필요한 곳에만 낸다 |
| 팀마다 독립 배포가 필요하고 운영 도구가 갖춰졌다 | 마이크로서비스 | 배포와 장애 범위를 팀 단위로 나눈다 |

## 자주 깨지는 곳

- 서비스는 나누고 DB는 같이 쓰면, 스키마 변경 때마다 여러 서비스를 같이 배포하는 분산 모놀리스가 된다.
- 서비스 사이 호출에 타임아웃을 두지 않으면, 재고 서비스가 느려질 때 주문 서비스 스레드까지 모두 묶인다.
- 한 요청 안에서 서비스를 줄줄이 동기 호출하면, 가장 느린 서비스가 전체 응답 시간을 정하고 하나만 죽어도 전체가 실패한다.
- 재시도하는 호출을 멱등하게 만들지 않으면, 타임아웃 뒤 재시도에서 재고가 두 번 잡힌다.
- 기능 하나를 바꿀 때마다 서비스 여러 개를 같이 배포해야 하면, 경계를 잘못 그은 것이고 나눈 비용만 내고 있다.
- trace ID를 서비스 사이에 넘기지 않으면, 장애가 났을 때 어느 서비스에서 시작됐는지 찾지 못한다.

## 운영에서 볼 것

- 서비스 사이 호출의 지연 시간 p99와 오류율, 타임아웃 횟수를 호출 대상별로 본다.
- 느린 요청 하나를 골라 트레이스에서 어느 서비스 구간이 시간을 썼는지 본다.
- 최근 배포 이력에서 같이 배포된 서비스 묶음을 센다. 매번 같이 나가는 묶음은 경계를 다시 볼 후보다.
- 보상이나 outbox 재처리가 쌓이는 건수를 본다. 늘어나면 서비스 사이 정합성이 자주 어긋나고 있다.

## 한 번에 설명하기

> 모놀리스는 한 번에 배포하는 구조이고, 마이크로서비스는 업무별로 따로 배포하고 네트워크로 부르는 구조입니다.
>
> 나누면 팀별 독립 배포와 장애 격리를 얻지만, DB 트랜잭션이 사라지고 타임아웃, 재시도, 보상, 분산 추적, 서비스별 운영 비용이 생깁니다.
>
> 그래서 저는 모듈 경계를 코드에서 먼저 지키는 모듈러 모놀리스로 시작하고, 배포 주기나 부하가 확연히 다른 모듈만 서비스로 뗍니다. 한 트랜잭션에서 같이 맞아야 하는 데이터는 같은 서비스에 둡니다.

## 꼬리 질문

> [!question]- 서비스마다 DB를 나누면 여러 서비스 데이터를 합친 조회는 어떻게 하나?
> 화면에 필요한 몇 개 값은 다른 서비스 이벤트를 받아 내 DB에 복제해 두고 읽습니다. 복제한 값은 조금 늦게 맞는다는 걸 화면과 업무가 받아들일 수 있어야 합니다. 정산처럼 여러 서비스를 크게 모아 보는 조회는 별도 저장소로 데이터를 모아서 처리합니다.

> [!question]- 분산 트랜잭션이 필요하면 2PC를 쓰지 않나?
> 2PC는 참여하는 모든 서비스와 DB가 같은 프로토콜을 지원해야 하고, 조정자가 결정을 내릴 때까지 참여자가 락을 쥐고 기다립니다. 서비스마다 저장소가 다르고 독립 배포를 하는 구조와 잘 맞지 않습니다. 그래서 각 서비스가 로컬 트랜잭션으로 commit하고 outbox로 이벤트를 내보내고, 실패하면 보상하는 방식을 씁니다.

> [!question]- 분산 모놀리스는 무엇이고 어떻게 알아보나?
> 서비스는 나눴는데 DB를 공유하거나 서로 동기 호출에 깊게 묶여서, 따로 배포할 수 없는 상태입니다. 기능 하나를 바꿀 때마다 서비스 여러 개를 같이 배포해야 하면 의심합니다. 나눈 비용은 다 내면서 독립 배포는 얻지 못한 상태입니다.

> [!question]- 모놀리스에서 서비스를 떼어 낼 때 무엇부터 하나?
> 먼저 코드 안에서 모듈 경계를 지키게 만들고, 다른 모듈의 내부 Entity나 Repository를 직접 쓰는 곳을 없앱니다. 그다음 그 모듈의 데이터를 다른 모듈이 직접 읽지 않게 하고, 마지막에 배포를 나눕니다. 순서를 거꾸로 하면 네트워크 호출로 바뀐 순환 의존이 남습니다.
