# 컨텍스트 스위칭 비용과 원리

컨텍스트 스위칭은 CPU가 지금 실행 중인 프로세스나 스레드의 상태를 저장하고, 다음 것의 상태를 복원하는 과정이다.

스레드를 너무 많이 만들면 실제 작업보다 전환에 쓰는 시간이 커진다. CPU 사용률은 높은데 처리량(throughput)이 낮다면 이걸 먼저 의심한다.

## 동작

```
Thread A 실행 중
  │
  ├─ 1. Thread A의 레지스터, PC, 스택 포인터를 PCB/TCB에 저장
  │
  ├─ 2. 스케줄러가 다음 실행할 Thread B 선택
  │
  ├─ 3. Thread B의 저장된 상태를 레지스터에 복원
  │
  └─ 4. Thread B 실행 재개

소요 시간: 수 마이크로초 (µs)
```

### 직접 비용과 간접 비용

| 구분 | 내용 |
|---|---|
| 직접 비용 | 레지스터 저장/복원, 커널 모드 전환 (~수 µs) |
| 간접 비용 | CPU 캐시 무효화 (Cache Miss 증가), TLB Flush |

더 큰 쪽은 간접 비용이다. 새로 올라온 스레드가 쓰는 데이터가 캐시에 없으면 메모리에서 다시 읽어 와야 한다.

## 프로세스 전환과 스레드 전환

| 구분 | 프로세스 전환 | 스레드 전환 (같은 프로세스 내) |
|---|---|---|
| 메모리 공간 | 전환 (Page Table 변경) | 공유 (변경 없음) |
| TLB | Flush 필요 | Flush 불필요 |
| 캐시 | 대부분 무효화 | 일부 유지 |
| 비용 | 높음 | 낮음 |

같은 프로세스 안의 스레드끼리는 메모리 공간이 같아서 전환 비용이 훨씬 작다.

## 운영에서 볼 것

```bash
# 시스템 전체 컨텍스트 스위칭 횟수
vmstat 1
-----procs--- ---system---
 r  b    in     cs
 3  0   1200   15000    ← cs: 초당 컨텍스트 스위칭 횟수

# 프로세스별 컨텍스트 스위칭
pidstat -w -p <PID> 1
# cswch/s: 자발적 (I/O 대기 등)
# nvcswch/s: 비자발적 (Time Quantum 초과, 우선순위 선점)
```

| 지표 | 의미 | 해석 |
|---|---|---|
| voluntary (cswch) | 자발적 전환 (I/O 대기, sleep) | I/O 바운드 작업에서 정상 |
| involuntary (nvcswch) | 비자발적 전환 (OS가 강제 선점) | 높으면 CPU 경합 |

원인을 볼 때는 두 값을 나눠서 본다. 자발적 전환이 많으면 I/O 대기, 비자발적 전환이 많으면 CPU 경합 쪽이다.

## 줄이는 방법

1. **스레드 수를 코어 수에 맞춘다.** CPU 코어에 비해 스레드가 너무 많지 않게 한다.
2. **스레드 풀을 쓴다.** 스레드 생성과 소멸을 반복하지 않는다.
3. **비동기 I/O를 쓴다.** I/O 대기 중에 스레드를 반환해 전환 횟수를 줄인다.
4. **Virtual Thread (Java 21)를 쓴다.** OS 스레드 수 자체를 줄여 전환 비용을 낮춘다.

```
전통적 모델 (Thread-per-Request):
200 요청 → 200 OS 스레드 → 빈번한 컨텍스트 스위칭

Virtual Thread:
200 요청 → 200 Virtual Thread → 소수의 OS 스레드(carrier)
→ I/O 대기 시 Virtual Thread만 교체, OS 스레드는 유지
→ OS 레벨 컨텍스트 스위칭 감소
```

## 자주 깨지는 곳

- **스레드를 늘리면 처리량도 비례해 는다고 생각한다.** 어느 선을 넘으면 전환 비용 때문에 오히려 떨어진다.
- **자발적/비자발적 전환을 구분하지 않고 원인을 찾는다.** 처방이 정반대라 엉뚱한 곳을 고친다.
- **I/O 대기가 원인인데 스레드 풀 크기만 줄인다.** 효과가 없다.

## 면접에서 말하기

> 컨텍스트 스위칭은 CPU가 실행 대상을 바꿀 때 상태를 저장하고 복원하는 과정이고, 레지스터 저장보다 캐시 무효화 같은 간접 비용이 더 큽니다. 같은 프로세스 안의 스레드 전환은 프로세스 전환보다 쌉니다. 저는 `vmstat`의 cs와 `pidstat`의 cswch/nvcswch를 나눠 보고, 비자발적 전환이 많으면 스레드 수를 줄이고 I/O 대기가 많으면 비동기 I/O나 Virtual Thread를 검토합니다.

## 꼬리 질문

> [!question]- 컨텍스트 스위칭이 많으면 어떤 증상이 나타나는가?
> CPU 사용률은 높지만 처리량(throughput)이 낮아집니다. `top`에서 `%sy`(system)가 높으면 커널에서 전환 비용이 많이 소모되고 있다는 의미입니다.

> [!question]- I/O 대기로 인한 컨텍스트 스위칭은 나쁜가?
> 자발적 전환 자체는 정상입니다. I/O를 기다리는 동안 다른 스레드가 CPU를 사용할 수 있으므로 효율적입니다. 문제는 너무 많은 스레드가 I/O를 기다려서 전환이 빈번해지는 경우입니다.

> [!question]- Virtual Thread가 컨텍스트 스위칭을 줄이는 원리는?
> Virtual Thread는 I/O 대기 시 OS 스레드(carrier)를 반환하고, JVM 내부에서 다른 Virtual Thread를 같은 carrier에 배정합니다. OS 레벨의 전환 없이 JVM 내부에서 경량 전환이 일어나므로 비용이 훨씬 작습니다.
