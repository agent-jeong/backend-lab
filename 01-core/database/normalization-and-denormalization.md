# 정규화와 반정규화 판단 기준

정규화는 같은 데이터를 한 곳에만 두도록 테이블을 나누는 설계다. 반정규화는 조회를 빠르게 하려고 일부러 중복을 두는 설계다.

정규화를 안 하면 상품 이름 같은 값이 여러 테이블에 흩어져, 고칠 때 한 곳을 빠뜨리면 값이 어긋난다. 반대로 너무 잘게 나누면 JOIN이 늘어 조회가 느려진다. 기준 없이 반정규화하면 어긋나는 데이터와 맞춰 줄 코드가 늘고, 나중에 구조를 되돌리기도 비싸다.

## 정규화 단계

### 제1정규형 (1NF)

모든 컬럼에 더 쪼갤 수 없는 값(원자값) 하나만 들어간다. 한 칸에 값이 여러 개 들어가면 안 된다.

```
❌ 비정규
| user_id | phones              |
|---------|---------------------|
| 1       | 010-1111, 010-2222  |

✅ 1NF
| user_id | phone      |
|---------|------------|
| 1       | 010-1111   |
| 1       | 010-2222   |
```

### 제2정규형 (2NF)

1NF를 지키면서 부분 함수 종속을 없앤다. 복합 기본키 중 일부만 보고 값이 정해지는 컬럼을 다른 테이블로 떼어 낸다.

```
❌ 부분 종속 (복합키: order_id + product_id)
| order_id | product_id | product_name | quantity |
|----------|------------|--------------|----------|
product_name은 product_id에만 종속 → 부분 종속

✅ 2NF: 분리
Orders: | order_id | product_id | quantity |
Products: | product_id | product_name |
```

나누기 전에는 상품 이름을 바꾸려면 그 상품이 들어간 주문 행을 전부 고쳐야 한다. 하나라도 빠뜨리면 같은 상품이 주문마다 다른 이름을 갖는다.

다만 실제 주문 항목에는 주문한 때의 상품 이름과 가격을 일부러 복사해 둔다. 나중에 상품 정보가 바뀌어도 이미 끝난 주문 내역은 그대로여야 하기 때문이다. 이건 조회를 빠르게 하려는 반정규화가 아니라 그 시점의 값을 남기는 스냅샷이다.

### 제3정규형 (3NF)

2NF를 지키면서 이행 함수 종속을 없앤다. 키가 아닌 컬럼이 또 다른 키 아닌 컬럼의 값을 정하면 떼어 낸다.

```
❌ 이행 종속
| employee_id | department_id | department_name |
department_name은 department_id에 종속 (employee_id → department_id → department_name)

✅ 3NF: 분리
Employees: | employee_id | department_id |
Departments: | department_id | department_name |
```

| 단계 | 제거 대상 | 한마디로 |
|---|---|---|
| 1NF | 반복 그룹, 비원자값 | 한 셀에 하나의 값 |
| 2NF | 부분 함수 종속 | 복합키 일부에만 종속되는 컬럼 분리 |
| 3NF | 이행 함수 종속 | 키가 아닌 컬럼끼리의 종속 제거 |

실무에서는 보통 3NF까지 맞춘다. BCNF 이상은 특별한 경우에만 따진다.

## 반정규화

정규화한 테이블에 일부러 중복을 넣어 조회를 빠르게 하는 방법이다.

| 기법 | 설명 | 예시 |
|---|---|---|
| 컬럼 중복 | 자주 조회하는 컬럼을 다른 테이블에 복사 | 주문 테이블에 `user_name` 추가 |
| 파생 컬럼 | 계산 결과를 미리 저장 | `order_count`, `total_amount` |
| 테이블 병합 | 항상 함께 조회하는 1:1 테이블 합치기 | user + user_profile 병합 |
| 요약 테이블 | 집계 결과를 별도 테이블에 저장 | 일별 매출 요약 |

## 언제 반정규화하나

| 상황 | 판단 |
|---|---|
| 조회가 훨씬 많고, 쓰기는 드물다 | 반정규화를 따져 본다 |
| JOIN이 3개 이상이고 데이터가 크다 | 반정규화를 따져 본다 |
| 값이 바뀌면 여러 곳을 같이 고쳐야 한다 | 반정규화 비용이 크다 |
| 항상 값이 바로 맞아야 한다 | 정규화를 유지한다 |
| 보고서나 대시보드 조회가 느리다 | 요약 테이블을 따져 본다 |

```
정규화 ←────────────────────────────→ 반정규화
정합성 높음                         조회 성능 높음
JOIN 많음                          중복 데이터
갱신 비용 낮음                      갱신 비용 높음
저장 공간 적음                      저장 공간 큼
```

순서는 이렇다.

1. 기본은 3NF로 설계한다.
2. 측정해서 실제로 느린 게 확인되면 반정규화를 따져 본다.
3. 반정규화할 때는 복사본을 무엇으로 맞출지(이벤트, 배치, 트리거 등)를 같이 정한다.
4. 반정규화한 컬럼과 테이블은 문서로 남긴다.

## 자주 깨지는 곳

- 나중에 느려질까 봐 미리 반정규화하면, 빨라지는 건 없이 맞춰 줄 일만 생긴다.
- 반정규화한 컬럼을 무엇으로 갱신할지 안 정하면, 원본과 복사본이 어긋난다.
- 정규화를 아예 안 하면, 같은 데이터를 여러 곳에서 고쳐야 하는 구조가 된다.
- 면접에서 "무조건 정규화"나 "무조건 반정규화"라고 답하면, 판단 기준이 없다는 뜻으로 들린다.

## 한 번에 설명하기

> 정규화는 같은 데이터를 한 곳에만 두도록 테이블을 나누는 설계이고, 실무에서는 보통 3NF까지 맞춥니다.
>
> 반정규화는 조회를 빠르게 하려고 일부러 중복을 넣는 것이라, 저는 측정해서 실제로 느린 곳이 있을 때만 합니다.
>
> 반정규화할 때는 원본이 바뀌면 복사본을 이벤트나 배치로 어떻게 맞출지까지 같이 정합니다.

## 꼬리 질문

> [!question]- 정규화와 반정규화를 선택하는 기준은?
> 처음엔 3NF로 만들고, 조회가 실제로 느려지면 그때 반정규화를 따져 봅니다. 반정규화는 쓰기를 비싸게 만드는 대신 읽기를 싸게 만드는 거래라고 생각합니다.

> [!question]- 반정규화한 데이터의 정합성은 어떻게 유지하는가?
> 이벤트로 갱신하거나, 배치로 맞추거나, DB 트리거를 씁니다. 어느 방법이든 원본이 바뀌었는데 복사본이 그대로 남는 경우가 없어야 합니다.

> [!question]- 1NF, 2NF, 3NF를 한 문장씩 설명하면?
> 1NF는 한 칸에 값 하나만 넣는 겁니다. 2NF는 복합키 중 일부에만 딸린 컬럼을 떼어 내는 거고, 3NF는 키가 아닌 컬럼끼리 서로 값을 정하는 관계를 없애는 겁니다.
