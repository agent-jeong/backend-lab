# 정규화와 반정규화 판단 기준

정규화는 중복을 없애 데이터 정합성을 지키도록 테이블을 나누는 설계다. 반정규화는 조회 성능을 위해 일부러 중복을 들이는 설계다.

정규화를 안 하면 같은 데이터가 여러 곳에 흩어져, 고칠 때 한 곳을 빠뜨리면 값이 어긋난다. 반대로 너무 잘게 나누면 JOIN이 늘어 조회가 느려진다. 기준 없이 반정규화하면 불일치와 갱신 비용이 늘고, 나중에 구조를 바꾸기도 비싸다.

## 정규화 단계

### 제1정규형 (1NF)

모든 컬럼이 원자값(atomic value)을 가져야 한다. 한 셀에 값이 여러 개 들어가면 안 된다.

```
❌ 비정규
| user_id | phones              |
|---------|---------------------|
| 1       | 010-1111, 010-2222  |

✅ 1NF
| user_id | phone      |
|---------|------------|
| 1       | 010-1111   |
| 1       | 010-2222   |
```

### 제2정규형 (2NF)

1NF에 더해 부분 함수 종속을 없앤다. 기본키의 일부에만 종속되는 컬럼을 떼어 낸다.

```
❌ 부분 종속 (복합키: order_id + product_id)
| order_id | product_id | product_name | quantity |
|----------|------------|--------------|----------|
product_name은 product_id에만 종속 → 부분 종속

✅ 2NF: 분리
Orders: | order_id | product_id | quantity |
Products: | product_id | product_name |
```

### 제3정규형 (3NF)

2NF에 더해 이행 함수 종속을 없앤다. 키가 아닌 컬럼이 다른 비키 컬럼을 결정하면 분리한다.

```
❌ 이행 종속
| employee_id | department_id | department_name |
department_name은 department_id에 종속 (employee_id → department_id → department_name)

✅ 3NF: 분리
Employees: | employee_id | department_id |
Departments: | department_id | department_name |
```

| 단계 | 제거 대상 | 한마디로 |
|---|---|---|
| 1NF | 반복 그룹, 비원자값 | 한 셀에 하나의 값 |
| 2NF | 부분 함수 종속 | 복합키 일부에만 종속되는 컬럼 분리 |
| 3NF | 이행 함수 종속 | 비키 컬럼 간 종속 제거 |

실무에서는 보통 3NF까지 적용한다. BCNF 이상은 특수한 경우에만 따진다.

## 반정규화

정규화된 테이블에 일부러 중복을 넣어 조회를 빠르게 하는 기법이다.

| 기법 | 설명 | 예시 |
|---|---|---|
| 컬럼 중복 | 자주 조회하는 컬럼을 다른 테이블에 복사 | 주문 테이블에 `user_name` 추가 |
| 파생 컬럼 | 계산 결과를 미리 저장 | `order_count`, `total_amount` |
| 테이블 병합 | 항상 함께 조회하는 1:1 테이블 합치기 | user + user_profile 병합 |
| 요약 테이블 | 집계 결과를 별도 테이블에 저장 | 일별 매출 요약 |

## 언제 반정규화하나

| 조건 | 판단 |
|---|---|
| 조회가 압도적으로 많고, 쓰기가 드물다 | 반정규화 검토 |
| JOIN이 3개 이상이고 데이터가 크다 | 반정규화 검토 |
| 데이터 변경 시 여러 곳을 함께 갱신해야 한다 | 반정규화 비용이 큼 |
| 실시간 정합성이 꼭 필요하다 | 정규화 유지 |
| 보고서/대시보드용 조회가 느리다 | 요약 테이블 검토 |

```
정규화 ←────────────────────────────→ 반정규화
정합성 높음                         조회 성능 높음
JOIN 많음                          중복 데이터
갱신 비용 낮음                      갱신 비용 높음
저장 공간 적음                      저장 공간 큼
```

순서는 이렇다.

1. 기본은 3NF로 설계한다.
2. 성능 문제가 측정으로 확인되면 반정규화를 검토한다.
3. 반정규화할 때 복사본을 어떻게 갱신할지(이벤트, 배치, 트리거 등)를 같이 설계한다.
4. 반정규화한 컬럼과 테이블은 문서로 남긴다.

## 자주 깨지는 곳

- **"나중에 느려질까 봐" 미리 반정규화한다.** 성능 이득은 없이 갱신 부담만 생긴다.
- **반정규화한 컬럼의 갱신 방법을 안 정한다.** 원본과 복사본이 어긋난다.
- **정규화를 안 한다.** 같은 데이터를 여러 곳에서 고쳐야 하는 구조가 된다.
- **면접에서 "무조건 정규화" 또는 "무조건 반정규화"라고 답한다.** 판단 기준이 없다는 뜻으로 들린다.

## 한 번에 설명하기

> 정규화는 중복을 없애 정합성을 지키는 설계이고, 실무에서는 보통 3NF까지 적용합니다. 반정규화는 조회 성능을 위해 일부러 중복을 넣는 것이라, 저는 측정된 병목이 있을 때만 검토합니다. 반정규화할 때는 원본이 바뀌면 복사본을 이벤트나 배치로 어떻게 갱신할지를 같이 설계합니다.

## 꼬리 질문

> [!question]- 정규화와 반정규화를 선택하는 기준은?
> 기본은 3NF로 설계하고, 실제 조회 성능이 문제될 때 반정규화를 검토합니다. 반정규화는 "쓰기 비용을 높여서 읽기 비용을 낮추는" 트레이드오프입니다.

> [!question]- 반정규화한 데이터의 정합성은 어떻게 유지하는가?
> 이벤트 기반 갱신, 배치 동기화, DB 트리거 등을 사용합니다. 어떤 방식이든 "원본이 바뀌면 복사본도 반드시 갱신된다"는 보장이 필요합니다.

> [!question]- 1NF, 2NF, 3NF를 한 문장씩 설명하면?
> 1NF: 한 셀에 하나의 값. 2NF: 복합키 일부에만 종속되는 컬럼 분리. 3NF: 비키 컬럼 간의 종속 제거.
