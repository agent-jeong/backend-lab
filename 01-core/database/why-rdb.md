# 관계형 DB를 사용하는 이유

관계형 DB(RDB)는 데이터를 테이블로 나눠 담고, 테이블 사이를 키로 잇는 저장소다. 여러 행을 한꺼번에 바꿔도 전부 반영되거나 전부 취소되게 해 주는 트랜잭션이 있다.

주문이나 결제처럼 숫자가 하나라도 어긋나면 안 되는 데이터를 RDB에 두는 이유가 이 트랜잭션이다. 반대로 RDB가 무엇을 지켜 주는지 모르고 쓰면, 캐시나 로그처럼 그런 보호가 필요 없는 데이터까지 습관처럼 RDB에 넣게 된다.

## RDB가 지켜 주는 것

### ACID

| 속성 | 뜻 | 실무에서 |
|---|---|---|
| 원자성(Atomicity) | 트랜잭션 안의 작업은 전부 반영되거나 전부 취소된다 | 결제 중 오류가 나면 차감한 재고까지 되돌린다 |
| 일관성(Consistency) | 트랜잭션 전후로 제약 조건이 깨지지 않는다 | FK, UNIQUE에 어긋나는 데이터는 들어가지 않는다 |
| 격리성(Isolation) | 동시에 도는 트랜잭션이 서로의 중간 상태를 덜 보게 한다 | 얼마나 막을지는 격리 수준이 정한다 |
| 지속성(Durability) | 커밋한 데이터는 서버가 죽어도 남는다 | 커밋 전에 로그(WAL)를 디스크에 먼저 쓴다 |

### 테이블과 관계

데이터는 행과 열로 이루어진 테이블에 담고, 테이블끼리는 FK로 잇는다. 조회할 때는 "어떤 데이터가 필요한지"만 SQL로 적으면 DB가 가져오는 방법을 고른다.

```sql
-- 주문과 사용자를 관계로 조회
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'COMPLETED';
```

## RDB와 NoSQL 고르기

| 기준 | RDB | NoSQL |
|---|---|---|
| 구조 | 스키마가 정해져 있다 | 스키마가 느슨하거나 없다 |
| 정합성 | 트랜잭션으로 맞춘다 | 대부분 시간이 지나면 맞춰진다(eventual consistency) |
| 조인 | 자유롭다 | 없거나 제한적이다 |
| 확장 | 주로 서버를 키운다(scale-up) | 서버를 늘리기 쉽다(scale-out) |
| 어울리는 데이터 | 주문, 결제, 회원 | 캐시, 세션, 대량 로그 |

보통 주문·결제·회원처럼 업무의 중심이 되는 데이터는 RDB에 두고, 캐시·세션·로그 같은 데이터는 NoSQL에 둔다.

## 정규화와 반정규화

정규화는 같은 데이터를 한 곳에만 두도록 테이블을 나누는 일이다. 같은 값이 여러 테이블에 있으면 한쪽만 고쳐져 어긋나기 쉽다. 정규화하면 고칠 곳이 하나로 줄어든다.

반정규화는 조회를 빠르게 하려고 일부러 중복을 두는 일이다. JOIN이 많아 조회가 느릴 때 쓰고, 그 대신 중복된 값을 맞춰 주는 일이 생긴다.

처음에는 정규화해서 만들고, 조회가 실제로 느려졌을 때만 반정규화한다. 자세한 기준은 [[normalization-and-denormalization]]에 있다.

## 자주 깨지는 곳

- 익숙하다는 이유로 저장소를 고르면, 데이터 성격과 맞지 않는 쪽을 쓰게 된다.
- 트랜잭션이 무엇을 되돌려 주는지 모르고 쓰면, 외부 API 호출처럼 되돌릴 수 없는 일까지 롤백될 거라고 기대하게 된다.
- 반정규화를 먼저 하면 중복을 맞추는 코드가 곳곳에 생기고, 하나라도 빠지면 데이터가 어긋난다.
- "RDB는 느리다"는 이유로 NoSQL을 고르면, 나중에 정합성 문제를 직접 풀어야 한다.

## 한 번에 설명하기

> RDB는 데이터를 테이블로 나누고 트랜잭션으로 묶어서, 여러 행을 바꿔도 전부 반영되거나 전부 취소되게 해 줍니다. 그래서 주문이나 결제처럼 어긋나면 안 되는 데이터는 RDB에 둡니다.
>
> NoSQL은 스키마가 자유롭고 서버를 늘리기 쉽지만 트랜잭션이 약해서, 캐시나 로그 같은 데이터에 씁니다.
>
> 테이블은 정규화해서 만들고, 조회가 실제로 느려졌을 때만 반정규화합니다.

## 꼬리 질문

> [!question]- 격리 수준을 가장 높게 두지 않는 이유는?
> 가장 높은 Serializable은 동시에 도는 트랜잭션을 거의 줄 세우듯 처리해서 느려집니다. 그래서 보통 Read Committed나 Repeatable Read를 쓰고, 꼭 막아야 하는 경합은 락이나 조건부 UPDATE로 따로 막습니다.

> [!question]- RDB는 왜 서버를 늘리기 어려운가?
> 트랜잭션과 JOIN이 여러 서버에 흩어진 데이터를 건드리면, 서버 사이를 오가는 시간과 분산 트랜잭션 비용이 생깁니다. 샤딩으로 나눌 수는 있지만, 샤드를 넘나드는 JOIN은 어려워집니다.

> [!question]- 반정규화는 언제 하나?
> 자주 읽히는데 JOIN 때문에 느린 테이블에 합니다. 읽기가 쓰기보다 훨씬 많은 곳이 대상입니다. 하고 나면 중복된 값을 맞추는 코드가 따로 필요합니다.
