# 관계형 DB를 사용하는 이유

RDB(Relational Database)는 데이터를 테이블 사이의 관계로 구조화하고, 트랜잭션으로 정합성을 보장하는 저장소다.

RDB가 무엇을 보장하는지 알아야 NoSQL과 비교해 고를 수 있다. 트랜잭션이 보장하는 것과 보장하지 않는 것, 정규화와 반정규화의 대가를 모르면 NoSQL이 더 맞는 자리에도 습관처럼 RDB를 쓰게 된다.

## RDB가 보장하는 것

### ACID

| 속성 | 의미 | 실무 영향 |
|---|---|---|
| Atomicity (원자성) | 트랜잭션은 전부 성공하거나 전부 실패 | 결제 중 오류 시 전체 롤백 |
| Consistency (일관성) | 트랜잭션 전후로 데이터 무결성 유지 | FK, UNIQUE 등 제약조건 보장 |
| Isolation (격리성) | 동시 트랜잭션이 서로 간섭하지 않음 | 격리 수준에 따라 다름 |
| Durability (지속성) | 커밋된 데이터는 장애 후에도 유지 | WAL(Write-Ahead Log) 기반 |

### 관계 모델

데이터를 테이블(행과 열)로 표현하고, 테이블 사이를 FK로 잇는다. SQL로 무엇을 원하는지만 선언하면 조회할 수 있다.

```sql
-- 주문과 사용자를 관계로 조회
SELECT o.id, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 'COMPLETED';
```

## RDB와 NoSQL 고르기

| 기준 | RDB | NoSQL |
|---|---|---|
| 데이터 구조 | 정형 (스키마 고정) | 비정형/반정형 (유연한 스키마) |
| 정합성 | ACID 보장 | 대부분 Eventually Consistent |
| 조인 | 자유롭게 가능 | 제한적 또는 불가 |
| 확장 방식 | Scale-up 중심 | Scale-out 용이 |
| 맞는 경우 | 정합성이 중요한 비즈니스 데이터 | 대량 로그, 캐시, 실시간 데이터 |

보통 주문, 결제, 사용자 같은 비즈니스 핵심 데이터는 RDB에, 캐시, 세션, 로그 같은 보조 데이터는 NoSQL에 둔다.

## 정규화와 반정규화

정규화는 중복을 없애고 테이블을 나눠 정합성을 높인다. 같은 데이터가 여러 곳에 있으면 고칠 때 어긋나는데, 정규화하면 UPDATE가 한 곳에서만 일어난다.

반정규화는 조회 성능을 위해 일부러 중복을 허용한다. JOIN이 많아 조회가 느릴 때 쓰고, 그만큼 정합성을 맞출 부담이 는다.

기본은 정규화이고, 조회 성능이 실제로 문제일 때만 반정규화한다. 자세한 기준은 [[normalization-and-denormalization]].

## 자주 깨지는 곳

- **기준 없이 익숙한 저장소를 쓴다.** 데이터 성격과 맞지 않는 쪽을 고르게 된다.
- **ACID를 설명하지 못한 채 트랜잭션을 쓴다.** 무엇이 롤백되고 무엇이 안 되는지 모른다.
- **정규화와 반정규화의 대가를 따지지 않는다.**
- **"RDB는 느리다"는 선입견으로 NoSQL을 고른다.** 나중에 정합성 문제를 겪는다.

## 면접에서 말하기

> RDB는 데이터를 테이블 관계로 구조화하고 ACID 트랜잭션으로 정합성을 보장합니다. 그래서 저는 주문이나 결제처럼 정합성이 중요한 데이터는 RDB에 둡니다. NoSQL은 유연한 스키마와 수평 확장이 장점이지만 강한 정합성을 보장하기 어려워서, 캐시나 로그 같은 보조 데이터에 씁니다. 설계는 정규화를 기본으로 하고, 조회가 병목일 때만 반정규화합니다.

## 꼬리 질문

> [!question]- ACID에서 Isolation이 완벽하지 않은 이유는?
> 완벽한 격리(Serializable)는 성능이 크게 떨어집니다. 실무에서는 성능과 정합성 사이에서 격리 수준을 선택합니다. 대부분의 경우 Read Committed 또는 Repeatable Read를 사용합니다.

> [!question]- RDB에서 Scale-out이 어려운 이유는?
> 트랜잭션과 JOIN이 여러 서버에 분산된 데이터를 대상으로 하면 네트워크 지연과 분산 트랜잭션 비용이 발생합니다. 샤딩으로 분산할 수 있지만, 크로스 샤드 조인이 어렵습니다.

> [!question]- 반정규화는 언제 하는가?
> 조회 빈도가 높고 JOIN 비용이 병목일 때 적용합니다. 읽기 비율이 쓰기보다 훨씬 높은 테이블이 대상입니다. 반정규화 후에는 데이터 동기화 로직이 추가로 필요합니다.
