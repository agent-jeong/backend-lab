# 인덱스 동작 원리와 설계 기준

인덱스는 테이블 데이터를 빨리 찾으려고 따로 유지하는 정렬된 자료구조(B-Tree)다.

조회는 빨라지지만 쓰기마다 인덱스도 같이 고쳐야 한다. 그래서 "어디에 걸까"만큼 "걸었는데 왜 안 타나", "몇 개까지 둘까"를 같이 판단해야 한다. 데이터가 늘수록 인덱스 없는 조회는 그만큼 느려지고, 복합 인덱스 컬럼 순서나 커버링 인덱스를 모르고 설계하면 인덱스가 있어도 소용이 없다.

## B-Tree

B-Tree(Balanced Tree)는 디스크 I/O를 줄이도록 만든 자기 균형 트리다.

- 한 노드에 **여러 개의 키**를 저장한다. 이진 트리와 다른 점이다.
- 모든 리프 노드가 같은 깊이에 있다.
- 노드가 꽉 차면 분할(split)하고, 비면 병합(merge)해서 균형을 유지한다.
- 노드 크기를 디스크 블록 크기에 맞추면 I/O 횟수가 가장 적다.

```
              [30]                    ← 루트 노드
            /      \
       [10, 20]    [40, 50]          ← 브랜치 노드 (내부 노드에도 데이터 존재)
       / |  \      / |   \
    [1-9][10-19][20-29][30-39][40-49][50-59]  ← 리프 노드
```

B-Tree는 루트, 브랜치, 리프 어느 노드에든 키와 데이터를 저장한다.

## DB가 쓰는 건 B+ Tree

DB 인덱스가 실제로 쓰는 것은 B-Tree의 변형인 B+ Tree다.

```
B-Tree:
         [30(data)]
        /          \
  [10(data), 20(data)]  [40(data), 50(data)]
  → 모든 노드에 데이터 존재

B+ Tree:
              [30]                         ← 내부 노드: 키만 저장 (라우팅 역할)
            /      \
       [10, 20]    [40, 50]               ← 내부 노드: 키만 저장
       / |  \      / |   \
    [1-9]→[10-19]→[20-29]→[30-39]→[40-49]→[50-59]  ← 리프 노드: 키+데이터, 연결 리스트
```

| 구분 | B-Tree | B+ Tree |
|---|---|---|
| 데이터 위치 | 모든 노드 | 리프 노드에만 |
| 내부 노드 역할 | 키 + 데이터 | 키만 (라우팅) |
| 리프 노드 연결 | 없음 | Linked List로 연결 |
| 범위 검색 | 트리를 다시 탐색해야 함 | 리프 노드를 순차 탐색 |
| 내부 노드 fan-out | 낮음 (데이터 공간 차지) | 높음 (키만 저장하므로 더 많은 키 수용) |

DB가 B+ Tree를 고르는 이유는 네 가지다.

1. **범위 검색**: 리프가 연결 리스트라 `WHERE id BETWEEN 10 AND 50` 같은 쿼리는 리프만 차례로 읽으면 된다.
2. **높은 fan-out**: 내부 노드에 데이터가 없으니 한 노드에 키를 더 많이 넣는다. 트리가 낮아지고 디스크 I/O가 준다.
3. **예측 가능한 성능**: 데이터가 모두 리프에 있어서 어떤 키를 찾든 탐색 깊이가 같다.
4. **순차 접근**: Full Scan이나 ORDER BY는 리프의 연결 리스트를 따라가면 끝난다.

## InnoDB의 B+ Tree 인덱스

```
              [30]
            /      \
       [10, 20]    [40, 50]
       / |  \      / |   \
    [1-9][10-19][20-29][30-39][40-49][50-59]
        (Clustered: 리프 = 행 데이터 / Secondary: 리프 = PK 값)
```

- 루트 → 브랜치 → 리프 순서로 내려간다.
- 리프에 무엇이 있는지는 인덱스 종류에 따라 다르다. InnoDB의 PK(Clustered) 인덱스는 리프에 **행 데이터 자체**가 있고, Secondary 인덱스는 리프에 PK 값이 있다. 행 주소(포인터)를 갖는 방식은 MyISAM, PostgreSQL heap 쪽 설명이다.
- 1000만 건이어도 디스크 접근 3~4번이면 찾는다.
- 정렬된 상태를 유지하므로 범위 검색과 정렬에 유리하다.
- 리프끼리 연결되어 있어 범위 검색 중에 트리를 다시 탈 필요가 없다.

### Clustered vs Non-Clustered

| 구분 | Clustered Index | Non-Clustered Index (Secondary) |
|---|---|---|
| 정의 | 데이터 자체가 인덱스 순서로 저장 | 별도 인덱스 구조에 데이터 위치 저장 |
| 개수 | 테이블당 1개 (보통 PK) | 여러 개 가능 |
| 리프 노드 | 실제 데이터 행 | PK 값 (→ Clustered Index로 다시 조회) |
| 조회 | PK 조회가 가장 빠름 | PK를 거쳐 데이터 접근 (이중 탐색) |

InnoDB에서는 PK가 Clustered Index다. Secondary Index로 찾으면 리프에서 PK 값을 얻고, 그 PK로 Clustered Index를 한 번 더 탐색한다.

## 복합 인덱스

```sql
CREATE INDEX idx_user_status_created ON orders (user_id, status, created_at);
```

복합 인덱스는 **왼쪽 컬럼부터 순서대로** 쓰인다.

```sql
-- 인덱스 사용 O
WHERE user_id = 1
WHERE user_id = 1 AND status = 'COMPLETED'
WHERE user_id = 1 AND status = 'COMPLETED' AND created_at > '2024-01-01'

-- 인덱스 사용 X (첫 번째 컬럼 누락)
WHERE status = 'COMPLETED'
WHERE created_at > '2024-01-01'
```

예외가 있다. MySQL 8.0.13+는 선두 컬럼 카디널리티가 낮으면 Index Skip Scan을 쓸 때가 있고, 조회 컬럼이 모두 인덱스에 있으면 인덱스 풀 스캔을 고르기도 한다. 둘 다 정상적인 range 탐색보다 느리다. 그래서 "선두 컬럼부터 조건을 건다"를 기본으로 설계한다.

컬럼 순서는 이렇게 정한다.

1. 동등 조건(=) 컬럼을 앞에 둔다.
2. 범위 조건(>, <, BETWEEN) 컬럼을 뒤에 둔다. 범위 조건 뒤의 컬럼은 인덱스를 타지 않는다.
3. 동등 조건끼리는 카디널리티(고유값 수)가 높은 컬럼을 앞에 두는 편이 유리하다. 단 1·2번(조건 형태)과 실제 쿼리 패턴이 카디널리티보다 우선한다.

## 커버링 인덱스

```sql
-- 인덱스: (user_id, status, created_at)

-- 커버링 인덱스 O: SELECT 컬럼이 모두 인덱스에 포함
SELECT user_id, status, created_at FROM orders WHERE user_id = 1;

-- 커버링 인덱스 X: amount는 인덱스에 없어서 테이블 접근 필요
SELECT user_id, amount FROM orders WHERE user_id = 1;
```

쿼리에 필요한 컬럼이 모두 인덱스에 있으면 테이블 데이터를 읽지 않고 인덱스만으로 끝낸다. 실행 계획의 `Using index`로 확인한다.

## 인덱스를 안 타는 경우

| 경우 | 이유 |
|---|---|
| `WHERE YEAR(created_at) = 2024` | 컬럼에 함수를 적용하면 인덱스 무효화 |
| `WHERE name LIKE '%검색어'` | 앞쪽 와일드카드는 B-Tree 탐색 불가 |
| `WHERE status != 'DELETED'` | 부정 조건은 인덱스 효율이 낮음 |
| `WHERE amount + 100 > 500` | 컬럼에 연산을 적용하면 인덱스 무효화 |
| 데이터 대부분이 조건에 해당 | 옵티마이저가 Full Scan이 더 빠르다고 판단 |

```sql
-- 잘못된 예: 함수 사용
WHERE YEAR(created_at) = 2024

-- 올바른 예: 범위 조건으로 변경
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
```

## 인덱스의 비용

인덱스는 공짜가 아니다.

- **INSERT**: 인덱스에도 값을 넣는다.
- **UPDATE**: 인덱스 컬럼이 바뀌면 인덱스도 고친다.
- **DELETE**: 인덱스에서도 지운다.
- **저장 공간**: 인덱스마다 별도 공간을 쓴다.

그래서 WHERE, JOIN, ORDER BY에 자주 쓰이는 컬럼에만 건다. 안 쓰는 인덱스는 쓰기만 느리게 만든다.

## 자주 깨지는 곳

- **WHERE 컬럼에 함수나 연산을 건다.** 인덱스가 있어도 타지 않는다.
- **복합 인덱스 컬럼 순서를 쿼리와 상관없이 정한다.** 선두 컬럼이 조건에 없으면 쓸모가 없다.
- **카디널리티가 낮은 컬럼(예: 성별)에 단독 인덱스를 건다.** 옵티마이저가 거의 고르지 않는다.
- **인덱스를 너무 많이 만든다.** 쓰기마다 고칠 인덱스가 늘어 INSERT/UPDATE가 느려진다.
- **앞쪽 와일드카드 LIKE에 인덱스를 기대한다.** B-Tree로는 탐색할 수 없다.

## 면접에서 말하기

> 인덱스는 B+ Tree 기반의 정렬된 자료구조입니다. InnoDB에서는 PK가 Clustered Index이고, Secondary Index는 리프에 PK를 들고 있어 PK로 한 번 더 찾아갑니다. 복합 인덱스는 왼쪽 컬럼부터 쓰이므로 저는 동등 조건을 앞에, 범위 조건을 뒤에 둡니다. 컬럼에 함수나 연산을 걸면 인덱스를 못 타고, 불필요한 인덱스는 쓰기를 느리게 하므로 실제 쿼리 패턴에 맞춰서만 만듭니다.

## 꼬리 질문

> [!question]- 인덱스를 걸었는데 안 타는 이유는?
> 컬럼에 함수/연산을 적용했거나, 복합 인덱스의 선행 컬럼이 조건에 없거나, 데이터 대부분이 조건에 해당해서 옵티마이저가 Full Scan을 선택한 경우입니다.

> [!question]- 커버링 인덱스란?
> SELECT, WHERE에 사용된 모든 컬럼이 인덱스에 포함되어 테이블 데이터에 접근하지 않고 인덱스만으로 쿼리를 처리하는 것입니다. 실행 계획에서 `Using index`로 확인합니다.

> [!question]- 인덱스를 많이 만들면 안 되는 이유는?
> INSERT, UPDATE, DELETE 시 모든 관련 인덱스를 함께 수정해야 해서 쓰기 성능이 떨어집니다. 저장 공간도 추가로 필요합니다.

> [!question]- PK가 BIGINT여야 하는 이유는?
> PK는 Clustered Index이자 모든 Secondary Index의 리프에 저장되는 값입니다. UUID(16~36 bytes)보다 BIGINT(8 bytes)가 인덱스 크기가 작아 캐시 효율과 조회 성능이 좋습니다.
